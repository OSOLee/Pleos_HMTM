# 변경 기록 (CHANGELOG)

HMTM 버전 규칙: MTM judge 0.13.1을 기반으로 HMTM에서 고친 내용은 `hmtm-주.부.수`로 표시한다. MTM의 버전 번호와 겹치지 않게 하기 위해서다. 엔진 코드를 바꾼 항목에는 **[MTM 동기화 대상]**을 붙인다.

기존 버전 규칙: `주.부.수`
- **부 버전**(0.x.0): 도표 묶음 추가, 엔진 규칙 추가처럼 판정 결과가 달라질 수 있는 변경
- **수 버전**(0.x.y): 버그 수정, 문서 수정처럼 기존 도표의 결과를 바꾸지 않는 변경

현재 버전은 `VERSION` 파일에 있고, 판정 결과(`result.json`)의 `engine_version`에도 기록된다.

## hmtm-0.1.1 (2026-11-09) A 보행자 질문 답을 판정 필드로 변환 [MTM 동기화 대상]
- 기반: hmtm-0.1.0. 엔진(`fault_engine.py`)과 규칙 파일은 그대로, 변환기(`adapter.py`)만 바꿈
- **[MTM 동기화 대상] 이유**: MTM에 보행자 규칙(hmtm-0.1.0의 `rules_pedestrian.json`)을 가져갈 때 이 변환도 같이 가야 한다.
  MTM의 A도 같은 질문(`crossing_place`, `ped_signal_at_crossing`)을 내므로, 변환 없이 규칙만 옮기면 "횡단보도 위·부근" 답이
  `ped_place`로 닿지 않아 보행자 도표가 늘 판단 보류가 되고, `green_flashing`은 B의 `flashing_green`과 맞지 않는다.
  옮길 것: `adapter.py`의 `_from_chapter_answers`·`CROSSING_PLACE_TO_PED_PLACE`·`PED_SIGNAL_VALUES`, `OPTIONAL_PARTY_FIELDS`의 `crossing_place`, `tests/test_adapter_fields.py`의 `ChapterAnswersTest`
- A 질문(`backend/src/app/chapters.py`) 답 중 이름·값만 바꾸면 뜻이 같은 것을 엔진 이름으로 바꿈
  - `crossing_place = on_crosswalk` → `ped_place = crosswalk`, `near_crosswalk` → `near_crosswalk`. 보행자(`person`) 당사자만, `ped_place`가 이미 있으면 그대로. 출처(`user`)도 옮김 → 사용자 답으로 적용된 결과에 "입증 필요"가 붙음
  - `ped_signal_at_crossing = green_flashing` → `flashing_green` (B의 신호 값 이름). 차53-1의 `red` 판단은 그대로
  - `crossing_place`를 `OPTIONAL_PARTY_FIELDS`에 추가 (A facts에 직접 들어와도 읽음)
- 바꾸지 않은 것 (추측하지 않고 비워 둠): `carriageway`(횡단보도 없는 차도), `sidewalk`(보도·길 가장자리)는 엔진 값 여럿에 걸쳐 `ped_place = None`. `ped_signal_at_crossing` 하나를 `ped_signal_at_start`·`ped_signal_at_impact` 둘로 나누지 않음
- 이 둘과 `CHAPTER_OF`의 `person` 누락은 A 요청으로 정리: `docs/A_REQUESTS.md`
- 판정 영향: 보행자 사고에서 "횡단보도 위·부근" 답이 이제 도표 선택에 쓰임. 차대차·차대자전거 결과는 그대로
- 테스트: judge 117개(+5, `tests/test_adapter_fields.py`의 `ChapterAnswersTest`), backend `tests/test_judge_category.py`에 A 답 → 변환기 경로 2개 추가

## hmtm-0.1.0 (2026-11-09) 사고 유형별 판정 구조, 차대보행자(보1~36)·차대자전거(거1~43) 도표 [MTM 동기화 대상]
- 기반: MTM judge 0.13.1
- 도표: 차대차 124개 + **차대보행자 45개**(제3편 제1장 보1~보36) + **차대자전거 55개**(제3편 제3장 거1~거43, 농기계 포함) = 224개. 새 도표는 모두 `source.verified: false` (원문 대조 전)

### 구조 (엔진)
- 엔진: 충돌 당사자의 차종(`cls`)으로 사고 유형을 정하고, 유형에 맞는 규칙 파일을 불러옴. 사용자에게 사고 유형을 묻지 않음
  - 사람(`person`) → 차대보행자 `rules_pedestrian.json`
  - 자전거(`bicycle`)·농기계(`farm_machine`) → 차대자전거 `rules_bicycle.json`
  - 그 밖의 자동차·이륜차, 또는 차종 정보 없음 → 차대차 `rules.json` (기존 동작과 같음)
  - 자전거와 보행자 사이의 사고는 범위 밖으로 보고 판정하지 않음
  - 화면에 보행자가 있어도 충돌 당사자가 아니면 차대차로 판정
- 수정요소: 공통 사전 `modifiers.json`에 유형별 추가 사전(`modifiers_pedestrian.json` 등)을 합쳐 씀. 운전자의 현저·중대한 과실은 공통 사전을 그대로 사용
- 판정 결과에 `accident_category`, `accident_category_reason` 추가. 아직 매핑하지 않은 유형이면 "도표가 아직 매핑되지 않았습니다"로 보고
- `judge(facts)`처럼 규칙을 넘기지 않을 때만 유형을 판단. 규칙을 직접 넘기면 기존처럼 그 규칙만 씀 (함수 이름·인자는 그대로)
- `rules.json`에 `category: car_car` 표시. 도표 내용은 그대로
- `run_judge.py`: 규칙 파일을 직접 고르지 않고 엔진의 유형 판단을 사용
- HMTM 연동: `backend/src/app/judge_bridge.py`가 `judge(facts, load_rules(), load_catalog())`로 차대차 규칙만 넘기던 것을 `judge(facts)`로 바꿈 (영상·블랙박스·차량 사건 모두 이 함수를 씀). `backend/tests/test_judge_category.py`가 A 형식 facts의 `pedestrian`·`person`·`bicycle`·`farm_machine`(답)이 이 경로로 차대보행자·차대자전거가 되는지 확인

### 차대보행자 (`rules_pedestrian.json`, `modifiers_pedestrian.json`)
- A = 자동차(이륜차·원동기장치자전거 포함), B = 보행자. 원문은 보행자 과실만 표기하므로 base는 A = 100 − 보행자 과실. 보35·보36은 원문 A·B를 바꿔 넣음
- 보행자 쪽 가감은 B에 원문 부호 그대로, 자동차 운전자의 현저·중대한 과실은 A에 +10/+20
- 장별 수정요소 38개: 야간·시야장애(하나만), 간선도로, 주택·상점가, 집단 횡단, 어린이·노인·장애인과 보호구역(하나만, 큰 쪽), 횡단금지 표지·시설(하나만), 횡단보도에서 10~30m, 고속도로 보행 요소 등
- 이 장의 자동차 제한속도 위반은 10km/h 이상부터 현저한 과실(`ped_speeding_10_20`, 20km/h 이상은 공통 사전의 중대한 과실과 하나만)

### 차대자전거 (`rules_bicycle.json`, `modifiers_bicycle.json`)
- A = 자전거(농기계·손수레·우마 포함), B = 자동차(원동기장치자전거 포함). 원문 A:B 그대로
- 장별 수정요소 25개: 자전거도로 부근·안(하나만), 어린이·노인·장애인, 진로 막힘, 안전모·보호장구(하나만), 자전거 운전자의 현저·중대한 과실 등
- 자동차 제한속도 위반 10km/h 이상부터 현저한 과실(`bike_car_speeding_10_20`), 자동차 졸음운전은 중대한 과실(`bike_car_drowsy`, +20)
