# facts.json 필드 설명

> 대상: B(규칙 판정) 담당 · 기준 코드: `feature/A` · 작성일: 2026-10-19 · 갱신: 2026-10-20
> facts.json은 A(영상 분석)의 최종 출력이자 B의 입력이다. 만드는 과정은 `docs/A_pipeline.md`에 있다.

공통 규칙은 이렇다.

- 좌표는 영상 크기를 1로 본 0~1 값이다. `[x, y]`에서 y는 아래로 갈수록 커진다.
- 위치(`pos`)는 박스 아래 중앙, 즉 바퀴가 땅에 닿는 점이다.
- 시간은 `frame`(0부터)과 `t`(초)를 같이 준다.
- 교차로 진입처럼 B가 계산에 쓰는 값은 모르면 `null`이다. 진행 방향(`movement`)과 화면 방향은 모르면 `"unknown"`이다. 어느 쪽이든 사용자에게 확인할 값은 `unknowns`에 질문이 생긴다.
- ★ 표시는 B가 요청해서 이번에 추가한 필드다.

## 1. 최상위

| 필드 | 예 (sample) | 뜻 |
|---|---|---|
| `schema_version` | `"0.2"` | 형식 버전. v0.3 확정 후 올린다 |
| `source` | `"yolo"` | 사실을 만든 출처 |
| `video` | `"data/videos/sample.mp4"` | 분석한 영상 |
| `scene` | `"scenes/sample.json"` | 사용한 장면 정의 파일 |
| `road_type` | `"no_center_line"` | 도로 종류. scene.json에 사람이 적은 값을 그대로 옮긴다 |
| `camera_type` | `"cctv"` | `camera_check`의 판단 (`cctv` / `blackbox` / `unknown`). `camera.json`이 없으면 `null` |
| `traffic_lights_detected` | `[]` | 화면에서 15프레임 이상 탐지된 신호등 목록 (`track`, `pos`, `first_frame`, `frames`). 그 교차로를 통제하는 신호인지는 모른다 (5장의 신호등 질문 참고) |
| `road` | `{"location": "intersection", "junction_type": "cross", "signal_present": false, "road_width": null}` | B가 읽는 도로 정보. 교차로 장면이면 `location`·`junction_type`(장면의 값. 사거리 `cross`, 삼거리 `t`. 예전 장면처럼 값이 없으면 `cross`)을 넣는다. 신호등이 하나도 안 잡히면 `signal_present: false`, 잡히면 `null`(질문으로 확인). `road_width`는 화면으로 추정하지 못해서 늘 `null`이다 (5장의 도로 폭 질문) |
| `fps` | `15.0` | 영상의 초당 프레임 수 |
| `collision` | 2장 | 충돌 정보. 순위가 가장 높은 충돌 하나만 들어간다 (7.1). 확정 충돌이 없으면 가장 그럴듯한 후보가 임시로 들어간다 |
| `parties` | 3장 | 충돌 당사자 두 명의 사실. 키는 추적 ID |
| `intersection_entry_order` | 3장 끝 | 두 당사자의 교차로 진입 순서와, 경계 오차에도 그 판단이 유지되는지 |
| `events` | 4장 | 사건을 시간순으로 나열한 목록 |
| `unknowns` ★ | 5장 | 판단하지 못한 값을 사용자에게 물을 질문 목록 |
| `params` | 6장 | 이 결과를 만들 때 쓴 기준값 |

## 2. `collision`

| 필드 | 예 | 뜻 |
|---|---|---|
| `frame`, `t` | `114`, `7.6` | 두 박스의 접촉이 시작된 시점 |
| `a`, `b` | `"79"`, `"96"` | 두 당사자의 추적 ID. `parties`의 키와 같다. ID 숫자 순서일 뿐 과실비율의 A·B와는 관계없다 (7.9 참고) |
| `zone` | `"road"` | 충돌 지점이 속한 영역 id |
| `pos` | `[0.3576, 0.3627]` | 충돌 지점. 두 당사자 바퀴 위치의 가운데 |
| `contact` | `0.417` | 겹친 넓이 ÷ 작은 박스 넓이. 0.3 이상이면 접촉으로 본다 |
| `interp` | `true` | 충돌 프레임의 위치가 앞뒤 프레임으로 보간한 값인지 |
| `confirmed` | `true` | `true`: 접촉 후 감속까지 확인한 충돌. `false`: 충돌을 확정하지 못해 후보 1위를 임시로 쓴 것. 이때 `unknowns`에 "부딪힌 두 객체" 질문이 있다 |

`confirmed: false`일 때 후보는 이렇게 고른다. 두 박스의 간격이 0.1 안으로 들어온 적이 있는 쌍 중에서(처음부터 붙어 있던 쌍은 제외), 둘 다 움직인 쌍, 먼저 가까워진 쌍, 간격이 작은 쌍 순으로 3개를 뽑는다. 충돌 프레임은 그 쌍의 간격이 가장 작았던 프레임이라 실제 접촉 순간과 다를 수 있다. 사고가 먼저 나고 그 뒤의 접촉은 대부분 사고의 결과라서 "먼저 가까워진 쌍"을 앞세운다. cc_150101에서는 31번 ↔ 60번(흰 승용차)이 1위로 뽑혔지만, AI Hub 프레임 라벨과 맞춰 보니 **틀린 쌍**이었다 (7.2 참고).

| `first_frame` | `33` / `41` | 처음 나타난 프레임 |
| `origin_zone` | `side_entry_left` / `road` | 처음 있었던 영역. 화면 밖(`out_of_roi`)은 건너뛴다 |
| `origin_approach` | `null` | 교차로에 들어오기 직전에 있던 영역 id (예: `appr_n`). 교차로 진입을 확인하지 못했으면 `null` |
| `entry_from` | `null` | 그 진입로의 방위 (`north` / `east` / `south` / `west`). scene.json의 `direction`에서 온다. B 엔진은 이 값이 있으면 방위로 좌우 관계를 판단한다 (7.12 참고) |
| `zone_at_collision` | `road` / `road` | 충돌 순간 자기 바퀴 위치의 영역 |

### 영역 진입

| 필드 | 예 | 뜻 |
|---|---|---|
| `enter_road` | `{"frame": 52, "t": 3.467}` | 차도 영역(`type: carriageway`)에 처음 들어간 시점. 교차로 영상에는 차도 영역이 없어서 보통 `null`이다 (7.8 참고) |
| `intersection_entry` ★ | `null` | 교차로(`type: intersection`) 진입 시점 |
| `intersection_entry_speed` ★ | `null` | 진입 직전 5프레임 동안의 속도. 단위는 화면 비율/초 |
| `stopped_before_entry` ★ | `null` | 교차로에 들어오기 직전 영역(진입로)에서 속도 0.01 미만이 5프레임 이상 이어졌으면 `true`, 아니면 `false`. 진입로 구간이 10프레임보다 짧거나 진입을 확인하지 못했으면 `null` |

`intersection_entry`는 세 가지 값 중 하나다.

| 값 | 뜻 | 예 |
|---|---|---|
| `{"frame", "t"}` | 진입로 같은 다른 영역에서 교차로로 들어가는 순간을 확인했다 | cc_150101 트럭: `appr_n`에서 50프레임에 진입 |
| `null` + `unknowns`에 질문 있음 | 교차로에 있었지만 들어가는 순간은 못 봤다 | 화면 끝에서 바로 교차로로 들어온 차, 처음부터 교차로 안에서 나타난 차 |
| `null` + 질문 없음 | 교차로에 들어간 적이 없다 | 교차로 영역이 없는 영상, 진입로에 서 있던 차 |

`intersection_entry_speed`와 `stopped_before_entry`는 진입이 `{frame, t}`일 때만 값이 있고, 나머지는 `null`이다. 교차로 영역의 id는 `intersection`으로 짓는다 (B의 변환기가 이 이름으로도 찾는다).

### 진행 방향

진행 방향은 두 가지 방법 중 하나로 정한다.

1. **진입로 기준 (`movement_from: "zones"`)**: 교차로에 들어온 진입로와, 충돌 전에 나간 진입로가 둘 다 보이면 방위로 정한다. 예를 들어 west에서 들어와 east로 나가면 직진, north로 나가면 좌회전이다. 화면 각도와 상관없어서 가장 믿을 만하다.
2. **각도 기준 (`movement_from: "angle"`)**: 처음 방향과 충돌 직전 15프레임(약 1초)의 이동 방향을 비교한다. 처음 방향은 교차로 진입을 확인했으면 진입 직전 15프레임, 아니면 궤적이 시작된 뒤 15프레임이다.

교차로에 들어갔는데 나간 쪽을 못 봤으면(교차로 안에서 부딪힌 경우) 각도 기준 결과는 확정하지 않는다. 충돌 직전의 급제동과 미끄러짐이 각도를 크게 바꾸기 때문이다 (7.7 참고). 이때 `movement`는 `unknown`으로 두고 질문을 보낸다.

추정값(`movement_guess`)은 먼저 **충돌 직전 진행 방향을 충돌 지점에서 앞으로 늘려 처음 닿는 진입로**를 나갈 쪽으로 보고 정한다(`ray`). 각도만 보면 원근 때문에 화면 위쪽 먼 차는 직진해도 30° 넘게 꺾여 보인다(cc_211208의 1번은 31°). 진입로 영역으로 보면 그 영향이 줄어든다. 닿는 진입로가 없으면 각도 기준(`angle`)으로 추정한다. 사용자 답이 없으면 이 추정값으로 판정한다(5장 끝).

| 필드 | 예 (79 / 96) | 뜻 |
|---|---|---|
| `movement` | `unknown` / `straight` | `straight`, `left_turn`, `right_turn`, `u_turn`, `unknown`. 각도 기준일 때 이동이 0.02보다 짧거나, 회전 각도가 30°·150°에서 ±10° 안쪽이거나, 이동이 0.03보다 짧으면 `unknown`. 교차로 안에서 충돌해 나간 쪽을 못 봐도 `unknown` |
| `movement_guess` | `null` | `unknown`으로 돌린 경우의 추정값. 그 밖에는 `null` |
| `movement_guess_from` | `null` | `ray`(충돌 직전 방향을 늘려 본 나갈 진입로) 또는 `angle`(각도) |
| `movement_from` | `angle` | `zones`(진입로 기준) 또는 `angle`(각도 기준) |
| `turn_deg` | `null` / `8.1` | 방향이 바뀐 각도. 양수는 화면에서 시계 방향(우회전)이다. ±30° 이상이면 회전, 150° 이상이면 유턴 |
| `heading_start` | `[0.0297, 0.0003]` | 처음 방향의 이동 벡터 (x, y). 회전하기 전 방향 |
| `heading_start_from` | `track_start` | 처음 방향을 잰 구간. `intersection_entry`(교차로 진입 직전) 또는 `track_start`(궤적 시작 직후) |
| `heading_before_collision` | `[-0.0137, -0.0013]` | 충돌 직전 15프레임 동안 움직인 벡터 |
| `disp_start` | `0.0297` | `heading_start`의 길이 |
| `disp_before_collision` | `0.0138` | `heading_before_collision`의 길이 |
| `direction_before_collision` | `unknown` / `away_from_camera` | 충돌 직전 화면 기준 방향. `away_from_camera`(화면 위로), `toward_camera`(화면 아래로), `rightward`, `leftward`, `unknown` |

### 속도와 정지

| 필드 | 예 (79 / 96) | 뜻 |
|---|---|---|
| `approach_speed` | `0.029` / `0.053` | 충돌 직전 10프레임 속도의 중앙값. 단위는 화면 비율/초 |
| `stop_frame` | `121` / `null` | 충돌 후 20프레임 안에 속도가 접근 속도의 40% 이하로 3프레임 연속 떨어진 시점. 조건을 만족하지 않으면 `null` |

### 진입 순서 (`intersection_entry_order`, 최상위)

두 당사자가 모두 교차로 진입을 확인했을 때만 값이 있고, 아니면 `null`이다.

| 필드 | 예 (cc_150101) | 뜻 |
|---|---|---|
| `first` | `"same_time"` | 먼저 들어간 당사자 id, 또는 `same_time`(차이 1초 미만, B의 차12 기준) |
| `diff_sec` | `0.2` | 두 번째 당사자 진입 − 첫 번째 당사자 진입 (초). `collision.a`, `b` 순서 기준 |
| `diff_range_sec` | `[-0.6, 0.867]` | 교차로 경계를 0.02 넓히고 좁혀 다시 쟀을 때 차이가 가장 작아지는 경우와 커지는 경우 |
| `robust` | `true` | 범위의 양 끝과 기본값의 판단(`first`)이 모두 같으면 `true`. 아니면 `unknowns`에 진입 순서 질문이 생긴다 |

교차로 영역을 네 모서리로 만들면 경계가 실제보다 몇 % 어긋날 수 있다. 모서리마다 오차가 따로 생기므로, 한 차는 넓힌 경계로 일찍, 다른 차는 좁힌 경계로 늦게 잡힌 극단까지 본다. cc_150101에서 손으로 그린 영역은 `[-0.6, 0.867]`로 `robust: true`, 네 모서리 영역은 `[-0.067, 1.0]`으로 1초 기준에 닿아 `robust: false`다.

B는 진입 순서를 `intersection_entry`의 시각 차이로 직접 계산한다. 사용자가 진입 순서 질문에 답하면 앱이 두 당사자의 `intersection_entry`를 답에 맞게 고쳐서 B에 넘긴다 (예: "거의 동시에"면 같은 시각으로).

## 4. `events`

모든 항목에 `frame`, `t`, `type`이 있고, 종류마다 필드가 더 붙는다. 프레임 순서로 정렬되어 있다.

| `type` | 추가 필드 | 뜻 |
|---|---|---|
| `appear` | `track`, `zone` | 당사자가 처음 나타났다 |
| `enter_zone` | `track`, `from`, `zone`, `zone_type` ★ | 다른 영역으로 옮겨 갔다 |
| `collision` | `a`, `b`, `zone` | 충돌 |
| `stop` | `track` | 충돌 후 멈췄다 |

`zone_type`은 scene.json에 적은 영역 종류(`intersection`, `approach`, `carriageway`, `side_access`, `roadside_parking` 등)다. 화면 밖(`out_of_roi`)이나 어느 영역에도 속하지 않은 곳(`unknown`)이면 `null`이다. 영역 id(`box`, `road` 등)는 영상마다 사람이 정하는 이름이라, 교차로 진입은 `zone_type == "intersection"`으로 찾아야 한다.

## 5. `unknowns` ★

| 필드 | 예 | 뜻 |
|---|---|---|
| `field` | `"parties.79.movement"` | 답이 들어갈 자리 |
| `question` | `"이 차량은 어느 방향으로 가고 있나요?"` | 사용자에게 보여 줄 질문 |
| `answer_type` | `"choice"` | `choice`(선택지에서 고름), `frame`(영상에서 장면을 고름), `pair`(두 객체 쌍을 고름) |
| `options` | `["straight", "left_turn", "right_turn", "u_turn", "unknown"]` | 선택지(저장할 값). 문자열 또는 `true`/`false`. `frame`이면 `null` |
| `choices` | `["직진", "좌회전", "우회전", "유턴", "모름"]` | `options`와 같은 순서의 한글 표시. `frame`이면 `null` |
| `model_guess` | `"right_turn"` | 모델이 추정한 값 (경계값이라 확정하지 않은 경우). 없으면 `null` 또는 필드 없음 |
| `evidence_frame` | `99` | 질문과 함께 보여 줄 장면 |

지금 만들어지는 질문은 열 종류다. 질문에 `depends_on`이 있으면 그 답이 맞을 때만 앱에 보인다 (신호 색 질문은 신호등이 "있음"일 때만).

| 대상 | 언제 | `answer_type` | `model_guess` | `evidence_frame` |
|---|---|---|---|---|
| `parties.<id>.movement` | 진행 방향이 `unknown` (이동이 짧음, 각도가 경계값 근처, 교차로 안에서 충돌해 나간 쪽을 못 봄), 또는 사용자가 표시한 당사자 | `choice` | 각도 기준 추정값 | 충돌 15프레임 전 (그보다 늦게 나타났으면 처음 나타난 프레임) |
| `parties.<id>.entry_from` | 들어온 진입로를 못 봄(`null`), 또는 사용자가 표시한 당사자 | `choice` (`north`/`east`/`south`/`west`, 보기는 "화면 위쪽 길" 등) | 궤적으로 구한 방위 | 처음 나타난 프레임 |
| `parties.<id>.intersection_entry` | 교차로 안에 있었지만 들어가는 순간을 못 봄 (facts 값은 `null`). 사용자가 표시한 당사자는 진입 순서 질문으로 대신함 | `frame` | 없음 | 교차로 안에서 처음 확인된 프레임 |
| `parties.<id>.cls` | 종류 표 중 1등 비율이 85% 미만, 또는 이륜차 보정 규칙이 다수결을 뒤집음(`cls_from: two_wheeler_rule`) | `choice` | 지금 `cls` 값 | 충돌 5프레임 전 |
| `parties.<id>.signal_at_entry`, `parties.<id>.signal_at_collision` | 신호등이 있다고 답했을 때만 (`depends_on: {"road.signal_present": true}`). 충돌 순간 색은 진입 뒤 화면 신호등 색이 바뀌었을 때만 묻고, 안 물으면 진입 때 답을 같이 씀 | `choice` (`green`/`green_arrow`/`yellow`/`red`/`flashing_yellow`/`flashing_red`/`none`) | 없음. 어느 신호등이 그 당사자 쪽인지 영상으로 못 정하고 색 분류도 0.70이라, 그 장면에서 본 신호등 색을 `light_hints`로만 붙임 (그림에도 `light red 0.91`처럼 적음) | 진입 프레임 / 충돌 프레임 |
| `road.signal_present` | 교차로 장면이면 항상 (신호등이 하나도 안 잡혀도 화면 밖에 있을 수 있어서. 교차로가 아니고 안 잡히면 "없음"으로 확정) | `choice` (`true`/`false`) | `false` (1차 범위는 신호 없는 교차로. 보인 신호등이 다른 교차로나 점멸 신호일 수 있음) | 첫 신호등이 나타난 프레임 |
| `collision.parties` | 충돌을 확정하지 못함 (`collision.confirmed: false`), 또는 확정 충돌이 2개 이상 | `pair` (`options`는 `[["31", "60"], ...]`). 보기는 순위 앞의 확정 충돌 5개 또는 후보, 그 뒤에 "닿은 채 나타난 쌍" 3개(`choices`에 "충돌 뒤 탐지" 표시). 순위는 7.1 | 자동으로 고른 쌍 | 고른 충돌 프레임 |
| `intersection_entry_order` | 경계 오차 안에서 진입 순서 판단이 바뀜 (`robust: false`), 또는 충돌 쌍에 사용자가 표시한 당사자가 있음 | `choice` (`[a, b, "same_time"]`) | 기본 판단(`first`), 진입을 못 봤으면 없음 | 두 진입 중 이른 프레임 |
| `road.center_line` | 교차로 장면이면 항상 | `choice` (`true`/`false`, 보기는 "있음 / 없음 (골목길)") | 없음 (답이 없으면 B에 넘기지 않음) | 0프레임 |
| `road.wider_road` | 교차로 장면이면 항상 | `choice` (`["equal", "north_south", "east_west"]`) | `equal`. 추정이 아니라 기본값이라 질문에 `"default": true`가 붙는다. 네 모서리 사각형의 변 길이로 추정해 봤지만, 원근 때문에 11개 장면 모두 남북 폭이 동서 폭의 1.8~3.9배로 나와 쓸 수 없었다 | 0프레임 |

`road.wider_road`는 B 규칙(차12~)이 두 도로 폭이 같은지(`scene.road_width`), 다르면 누가 넓은 도로에 있었는지(`on_wider_road`)를 요구해서 넣었다. 답이 `north_south`면 `entry_from`이 north·south인 당사자가 넓은 도로에 있었던 것으로 본다 (`entry_from` 질문에 답이 있으면 답을 씀).

**사용자가 표시한 당사자** (`parties.<id>.source: "user"`): YOLO가 놓친 당사자를 사용자가 한 프레임에서 박스로 표시하면, 추적기(Vit)가 그 박스에서 앞뒤로 따라가 궤적을 만든다(`src/app/tap_track.py`). 평가 영상 11개에서 정답 박스로 시험해 보니 충돌 전 구간을 맞게 따라간 비율이 33~40%였다. 작고 빠른 이륜차를 충돌 전부터 따라가기 어렵다. 그래서 이 당사자는 궤적에서 나온 사실(진행 방향, 온 길, 진입 순서)을 추정값으로만 보여 주고 항상 묻는다.

### 답을 반영하는 방법 (`run_app.py`, `src/app/answers.py`)

사용자 답은 `{field: 값}` 형태의 JSON이다. 대부분은 facts를 고치지 않고 B 판정 모듈의 가정(`assumptions`)으로 넘긴다. B가 그 값의 출처를 `user`로 기록한다.

| 질문 | B에 넘기는 값 |
|---|---|
| `parties.<id>.movement`, `parties.<id>.cls`, `parties.<id>.entry_from` | `parties.<id>`의 같은 이름 값 |
| `parties.<id>.intersection_entry` (프레임) | `parties.<id>.intersection_entry_t` = 프레임 / fps |
| `intersection_entry_order` | 먼저 들어간 쪽 `entry_lead_sec` = max(측정 차이, 1초), 상대는 음수. 동시면 둘 다 0 |
| `road.signal_present` | `signal.state` = `normal` / `none` |
| `parties.<id>.signal_at_entry`, `signal_at_collision` | `parties.<id>`의 같은 이름 값. 충돌 순간 답이 없으면 진입 때 답을 같이 씀 |
| `road.center_line` | `scene.center_line`, 그리고 `scene.road_class` = `general`(있음) / `side_street`(없음). B 변환기가 중앙선 없는 도로를 골목길로 보는 것과 같은 기준 (차14가 골목길 여부를 요구) |
| `road.wider_road` | `scene.road_width` = `equal` / `different`, 다르면 당사자별 `on_wider_road` |

`collision.parties`만 예외다. 고른 쌍으로 충돌을 다시 정해야 해서 `detect_collision.run(out_dir, pair=[a, b])`부터 다시 돌린다. 이때 collision.json의 `auto_events`에 자동 검출 결과를 남긴다.

B는 `unknowns`에 남아 있는 값을 "확정되지 않은 사실"로 다루면 된다.

### 답이 없어도 결과를 내는 방법 (`answers.fill_guesses`)

CCTV에서 당사자를 잡았으면 사용자 입력 없이도 결과가 나와야 한다. 그래서 답이 없는 질문은 `model_guess`(진행 방향·온 길·종류 추정값, 신호등 "없음", 도로 폭 기본값 "비슷함")로 채운 판정용 사본 `facts_judge.json`을 만들어 판정한다. 이렇게 채운 값은 B에 사용자 입력이 아니라 facts의 값으로 넘어간다. 앱 응답에는 `verdict.provisional: true`와 채운 질문 목록 `verdict.auto_filled`가 붙는다. 질문은 "확인하면 결과가 바뀔 수 있는 쟁점"으로 보여 준다.

사용자 입력 없이 돌린 결과 (2026-10-21, 기본 YOLO): 11개 중 cc_211208 하나가 정답 비율과 같았다(차12-1(다) 30 : 70). 나머지는 당사자를 못 잡았거나(8개), 고른 쌍이 틀렸거나(180304), 교차로를 가로지르는 사고가 아니었다(200511).

`parties.<id>.cls`는 질문이 있어도 facts 값을 비우지 않는다. B가 종류에 따라 도표의 장을 고르기 때문에, 비워 두면 판정 자체를 못 한다. 질문이 남아 있으면 추정값으로 읽으면 된다.

`road.signal_present`를 항상 묻는 이유는, 화면에 신호등이 보여도 그 교차로를 통제하는 신호가 아닐 수 있기 때문이다 (멀리 있는 다른 교차로, cc_200303처럼 라벨은 "신호등없음"인데 야간 점멸 신호가 켜진 경우).

## 7. 한계와 예시

아래 예시는 실제로 돌려 본 영상 세 개에서 나온 결과다.

- `sample.mp4`: 골목길 CCTV, 골목에서 나온 차와 이륜차
- `cc_3_150101`: 비신호 사거리 CCTV, 낮, 덤프트럭과 승용차
- `cc_3_200303`: 비신호 사거리 CCTV, 야간, SUV와 자전거

### 7.1 충돌은 하나만 고른다

`build_facts`는 검출된 충돌 중 순위가 가장 높은 것을 사고로 보고 당사자를 정한다 (순위는 아래). 그런데 차가 화면에서 겹쳐 보이는 것만으로도 충돌 후보가 생긴다.

탐지 설정을 바꿔 가며 실험할 때 sample 영상에서 실제 사고(112프레임, 차 ↔ 이륜차)보다 앞선 26프레임에 가짜 충돌이 하나 더 잡혔다. 골목 입구에서 앞뒤로 줄지어 움직이던 차 두 대가 화면에서 겹쳐 보였고, 그중 한 대가 마침 속도를 줄여서 "접촉 후 감속"이라는 조건을 만족했다. 이 경우 facts.json의 당사자는 사고와 무관한 두 차가 된다.

지금 쓰는 탐지 설정(yolov8s, 입력 640, 낮은 추적 문턱)에서는 sample의 가짜 충돌이 나오지 않는다. 다른 영상에서 같은 일이 생기지 않는다는 보장은 없다.

그래서 확정 충돌이 2개 이상이면 하나를 고르되, `unknowns`에 "부딪힌 두 객체" 질문을 남겨 사용자가 고칠 수 있게 했다. 고르는 순서는 두 번 바뀌었다.

1. 처음에는 궤적 id 순서였다. 문서에 적힌 "처음 검출된 충돌"과 맞지 않아서 시간순으로 바꿨다. cc_211208은 충돌이 3개 검출되고(78, 81, 81프레임) 시간순 첫 번째가 정답이다.
2. 평가 영상을 24개로 늘리자(2026-10-24) 시간순이 크게 틀렸다. 확정 충돌이 150101은 44개, 211119는 15개 나왔고, 대부분 서 있는 차 앞을 다른 차가 지나가며 화면에서 박스만 겹친 가짜였다. 영상 앞부분의 가짜가 먼저 뽑혔다. 또 옆면끼리 부딪힌 차대차 충돌은 박스가 맞닿기만 하고 0.18~0.25만 겹쳐서, 접촉 기준(겹침 0.3)에 아예 걸리지 않았다.

지금 규칙은 이렇다 (`detect_collision.py`).

- 접촉: 작은 박스 넓이 대비 겹침이 `CONTACT_MIN`(0.1) 이상이거나, 두 박스가 `TOUCH_GAP`(0.005) 안으로 맞닿음. 바닥 높이 차이가 `DEPTH_TOL` 이하인 조건은 그대로다
- 순위: 둘 다 접촉 전에 움직이고 있던 충돌(`both_moving`) → 추적기가 확정한 궤적끼리의 충돌(조각이 안 낌) → 시간순. 맨 앞이 자동으로 고르는 충돌이다. 진짜 충돌은 대부분 두 차가 모두 움직이다 부딪혔다
- 질문 보기: 순위 앞의 충돌 `PAIR_OPTIONS`(5)개와 닿은 채 나타난 쌍 `BORN_OPTIONS`(3)개. 같은 순위로 정렬한다 (`build_facts.py`)

분석한 평가 영상 17개에서 자동으로 맞힌 당사자가 3개에서 7개로 늘었고, 자동으로 맞히거나 질문 보기에 정답이 든 영상은 11개다. 기준값을 이 17개로 정했으니, 재학습 모델이 나오면 다시 확인한다.

### 7.1.1 충돌 뒤에야 탐지된 당사자

이륜차는 충돌 직전까지 못 잡고, 충돌 뒤 상대 차와 겹친 채로 처음 잡히는 경우가 많다. 충돌 판정은 "떨어져 있다가 닿음"을 요구하므로 이런 쌍은 충돌이 될 수 없다.

- cc_180304: 라벨상 충돌은 49~51프레임인데, 우리 이륜차 궤적(167번)은 59프레임에 차(68번)와 닿은 채 처음 나타났다. 그 대신 나란히 달리며 화면에서 겹친 두 차(123↔162, 139↔162)가 확정 충돌이 됐다.

`detect_collision`은 이런 쌍을 `born_candidates`로 따로 모은다. 조건은 세 가지다.
- 두 궤적이 같이 보이는 첫 프레임이 한쪽의 시작 프레임이다.
- 거기서부터 3프레임 연속 닿아 있다.
- 그 뒤 한쪽이 멈춘다.

이 쌍은 자동 답으로 쓰지 않고 질문 보기에만 넣는다. 자동 답으로 쓰는 방식도 시뮬레이션해 봤다. cc_180304는 맞게 바뀌었지만, cc_200511에서는 진짜 충돌(80프레임)보다 앞선 가짜 쌍(27프레임)이 잡혀 맞던 결과가 틀어졌다.

### 7.2 충돌을 확정하지 못하면 후보로 대신하고, 당사자를 놓치면 그것도 못 한다

충돌 확정에는 "두 박스가 겹치고, 직후 한쪽이 감속"이 필요하다. 이 조건을 못 채우면 가까워진 쌍 중 1위 후보를 임시 충돌로 쓰고 사용자에게 확인을 받는다 (2장 `confirmed`).

- cc_150101: 충돌을 확정하지 못해 후보 1위 31번 ↔ 60번(흰 승용차)이 임시 충돌이 되었고, B 판정에서 두 차를 직진으로 두면 차12-1(가) 40 : 60이 나와 AI Hub 정답(A 40 : B 60)과 숫자가 같았다. **그런데 이건 우연이었다.** AI Hub 프레임 라벨과 맞춰 보니 실제 당사자는 북쪽에서 내려온 덤프트럭(A)과 동쪽 화면 끝에서 들어와 왼쪽으로 간 차(B)이고, 흰 승용차는 당사자가 아니었다. 우리 31번 궤적은 A 트럭 조각(6~66프레임)과 B 차량 조각(71~84프레임)이 이어붙여진 것이었다. A가 사라진 자리 근처(거리 0.039)에 B가 5프레임 뒤 나타나서 같은 차로 이어붙였다. 게다가 충돌 순간(79~89프레임)에는 두 차가 같은 프레임에 함께 탐지된 구간이 없어서, 이어붙이기를 고쳐도 충돌을 찾을 수 없다.
- cc_200303: 야간에 어두운 옷을 입은 자전거 운전자를 시험한 탐지 설정 세 가지(yolov8n 입력 1280·640, yolov8s 입력 640) 모두에서 한 번도 찾지 못했다. 당사자 한 명이 아예 없어서 후보도 엉뚱한 쌍이 되거나 없다. 이 경우는 탐지 모델을 다시 학습해야 해결된다.

후보도 없으면(가까워진 쌍이 하나도 없음) 지금처럼 facts.json 없이 멈춘다.

### 7.3 승용차와 이륜차를 잘 구분하지 못한다

`cls`는 COCO 데이터로 미리 학습된 YOLO 모델이 프레임마다 낸 판정을 모아 다수결로 정한다. 위에서 내려다본 오토바이를 승용차나 트럭으로 판정하는 일이 잦아서, 오토바이 표가 3개 이상이면 이륜차로 보는 보정 규칙을 넣었다. 이 규칙이 반대 방향으로도 틀린다.

| 영상 | 실제 | 표 (car / truck / motorcycle 등) | 결과 |
|---|---|---|---|
| sample | 이륜차 | car 30, truck 38, motorcycle 8, person 2 | `two_wheeler` (맞음) |
| cc_200303 | SUV | car 86, motorcycle 13, person 1 | `two_wheeler` (틀림) |

비율로 바꿔도 해결되지 않는다. 진짜 이륜차의 오토바이 표 비율은 10%(8/78)인데 SUV는 13%(13/100)로 오히려 높다. 차대차 사고가 차대이륜차로 바뀌면 적용할 인정기준 도표 자체가 달라지므로, B는 `cls`를 확정된 값으로 믿지 않는 편이 안전하다.

`car`, `truck`, `bus`도 섞인다. cc_150101의 덤프트럭은 궤적 앞부분이 `car`로 38번, 뒷부분이 `truck`으로 10번 잡혀서 `car`가 되었다. 대형차 가산(+5)을 적용할 때도 이 값을 그대로 믿기 어렵다.

그래서 두 경우에 `unknowns`에 "이 객체의 종류는?" 질문을 넣는다.

- 1등 종류의 표 비율이 85% 미만: sample의 이륜차(1등이 car 44%)와 cc_150101의 덤프트럭(car 79%)이 여기에 걸린다.
- 이륜차 보정 규칙이 다수결을 뒤집음(`cls_from: two_wheeler_rule`, 2026-10-24 추가): cc_200303의 SUV는 car 표가 86%라 첫 조건에 안 걸려서, 아무 질문 없이 이륜차로 넘어갔다. 평가 11개의 당사자 중 이 규칙이 다수결을 뒤집은 것은 셋이다. cc_200303의 1번(SUV, 틀림), cc_180304의 167번(이륜차, 맞음, car 52 / motorcycle 21), cc_180629의 100000번 조각(이륜차, 맞음, 원래도 표 비율 79%라 질문이 있었음). 규칙이 맞을 때가 더 많아서 값은 그대로 두고 확인만 받는다.

- 사람(person)으로만 잡혔는데 빠름(`cls_from: fast_person`, 2026-10-24 추가): 위에서 내려다본 자전거·오토바이는 탈것은 못 잡고 탄 사람만 잡는 경우가 많다. 1초에 자기 박스 높이의 0.8배(`RIDER_HS`) 이상 움직이면 묻는다. 평가 영상에서 이륜차·자전거 당사자 궤적 6개 중 5개가 0.93~1.65, 걷는 사람 20개 중 17개가 0.44 이하였다. 값은 `pedestrian` 그대로 두고 확인만 받는다.

질문의 추정값(`model_guess`)은 보정 규칙을 거친 `cls`다. 표가 한쪽으로 몰렸는데 틀린 경우(예: 모든 프레임에서 오토바이를 car로 판정)는 여전히 질문이 생기지 않는다. AI Hub 데이터로 모델을 다시 학습시키는 것이 근본 해결책이다.

### 7.4 속도는 카메라와의 거리에 따라 다르게 나온다

속도는 화면 위에서 움직인 거리(화면 비율)로 잰다. 같은 속도로 달려도 카메라에서 먼 차는 화면에서 작게 움직이므로 느리게 나온다.

cc_150101에서 교차로 진입 속도는 트럭 0.038, 승용차 0.070이었다. 트럭은 화면 위쪽(카메라에서 먼 곳), 승용차는 화면 왼쪽 가운데(더 가까운 곳)에서 들어왔다. 이 숫자만 보면 승용차가 두 배 가까이 빠른 것 같지만, 실제 속도 차이는 알 수 없다.

같은 차 안에서 시점별로 비교하는 것(예: 진입 속도보다 충돌 직전 속도가 줄었는지)은 의미가 있다. 서로 다른 두 차의 속도를 비교해서 "과속"이나 "더 빨랐다"를 판단하는 규칙은 피해야 한다. 바닥 기준점으로 화면을 위에서 내려다본 좌표로 바꾸면(호모그래피 변환) 해결할 수 있지만 아직 하지 않았다.

### 7.5 교차로 진입 시점은 바퀴 위치 기준이고, 차이가 작으면 믿기 어렵다

진입 시점은 박스 아래 중앙점이 교차로 영역 경계를 넘은 프레임이다. 실제로는 차 앞부분이 그보다 먼저 들어간다. 그 차이는 차 길이와 진행 방향, 카메라 각도에 따라 달라진다. 앞부분이 긴 덤프트럭과 승용차를 비교하면 같은 순간에 경계에 닿아도 바퀴 기준 진입 시점이 다르게 나올 수 있다.

cc_150101에서 트럭은 50프레임, 승용차는 53프레임에 진입해서 차이가 3프레임(0.2초)이다. 이 정도면 "트럭 선진입"이라고 단정하기 어렵다. 이 영상은 어안 렌즈라 화면 가장자리가 휘어 있어서 영역 경계 자체도 몇 프레임 오차가 있다.

B는 진입 시각 차이 1초를 기준으로 동시 진입, 선진입, 후진입을 나눈다 (차12, v0.8.0).

진입 시각은 교차로 영역 경계를 어디에 두느냐에도 민감하다. 같은 cc_150101에서 경계만 바꿔 쟀더니 이렇게 나왔다.

| scene | 트럭 진입 | 승용차 진입 | 차이 | B 판단 |
|---|---|---|---|---|
| 손으로 그린 8각형 | 50 | 53 | 0.2초 | 동시 진입 |
| 네 모서리 (연석 모서리) | 55 | 61 | 0.4초 | 동시 진입 |
| 네 모서리 (2~3% 어긋나게) | 50 | 66 | 1.07초 | 트럭 선진입 |

어안 렌즈 때문에 왼쪽 횡단보도가 휘어 있어서, 네 점을 이은 직선 변이 실제 경계와 어긋나는 만큼 승용차의 진입이 늦게 잡혔다. 그래서 경계를 0.02 넓히고 좁혀 다시 재고, 진입 순서 판단이 바뀌면 질문으로 넘긴다 (3장 `intersection_entry_order`). 네 모서리 영역은 `robust: false`로 질문이 생기고, 손으로 그린 영역은 확정된다.

### 7.6 진입 순간을 못 보면 `null`이 되고 질문이 생긴다

교차로 영역이 화면 끝에 닿아 있으면, 그쪽에서 들어오는 차는 화면에 나타나는 순간 이미 교차로 안이다. cc_150101은 오른쪽 도로가 화면 밖으로 이어져서 교차로 영역이 화면 오른쪽 끝까지 닿는다. 오른쪽에서 오는 차가 당사자였다면 `intersection_entry`는 `null`이 되고, `unknowns`에 "교차로에 들어간 순간을 골라 주세요" 질문이 생긴다. 이 질문이 있는지로 "교차로에 안 들어감"(질문 없음)과 구분한다.

이 경우 진입 시점을 "처음 보인 시점"으로 넣지 않은 이유는, 그 값이 실제보다 늦은 시점이라 선진입 판단을 뒤집을 수 있기 때문이다.

### 7.7 진행 방향은 화면 기준이고, 천천히 움직이면 판단하지 못한다

`movement`와 `turn_deg`는 화면 위의 이동 방향으로 계산한다. 지도 기준 방향이 아니다.

- 천천히 움직인 경우: sample의 79번 차량은 골목에서 천천히 빠져나와 충돌 직전 1초 동안 0.0138밖에 움직이지 않았다. 기준(0.02)보다 짧아서 `movement`가 `unknown`이 되었고, `unknowns`에 진행 방향 질문이 생겼다.
- 원근과 렌즈 왜곡: 카메라 쪽으로 다가오는 차는 화면에서 아래로 내려오면서 점점 크게 보인다. 바퀴 위치가 화면 가장자리 쪽으로 휘어 가면 실제로는 직진인데 각도가 몇십 도 바뀐 것처럼 보일 수 있다. cc_150101 같은 어안 렌즈는 이 효과가 더 크다.
- 충돌 직전 1초를 기준으로 하므로, 충돌 직전에 핸들을 꺾은 차는 회전으로, 회전을 일찍 끝낸 차는 직진으로 나올 수 있다.
- 충돌 순간의 움직임: 충돌 직전에는 급제동, 미끄러짐, 다른 차와의 겹침으로 각도가 크게 흔들린다. 그래서 교차로 안에서 충돌해 나간 쪽을 못 본 경우에는 각도 결과를 확정하지 않고 질문으로 보낸다. (cc_150101의 31번에서 충돌 직전 이동이 `[-0.158, 0.008]`로 왼쪽으로 크게 꺾여 128.7°가 나왔는데, 처음에는 트럭이 미끄러진 것으로 봤다. 정답 라벨과 맞춰 보니 다른 차(B)의 궤적이 이어붙여진 것이었다. 7.2 참고.)
- 경계값: 회전 각도가 29°면 직진, 31°면 우회전이라 2° 차이로 도표가 바뀐다. 그래서 각도가 20~40°, 140~160°이거나 이동이 0.03보다 짧으면 `movement`를 `unknown`으로 두고 질문을 보낸다. 모델이 추정한 값은 `movement_guess`와 질문의 `model_guess`에 남는다.

### 7.8 `enter_road`는 교차로 영상에서 보통 비어 있다

`enter_road`는 차도 영역(`type: carriageway`)에 처음 들어간 시점이다. sample처럼 골목에서 큰길로 나오는 장면을 위해 만든 필드다. 교차로 영상의 scene.json은 교차로(`intersection`)와 진입로(`approach`)로 나누고 차도 영역을 따로 두지 않아서 `null`이 된다. 교차로 사고는 `intersection_entry`를 쓰면 된다.

### 7.9 `a`, `b`는 과실비율의 A, B가 아니다

`collision.a`와 `collision.b`는 추적 ID를 숫자 순서로 놓은 것뿐이다. 과실비율 "A : B"의 A가 어느 차인지는 정하지 않았다.

AI Hub 라벨에는 과실비율이 `accident_negligence_rateA`, `accident_negligence_rateB`로 나뉘어 있고(예: cc_150101은 A 40 : B 60), 프레임 라벨에 어느 객체가 A이고 B인지 표시되어 있다. 평가할 때는 이 표시와 우리 추적 ID를 맞춰야 한다. 앱에서 사용자 영상의 A를 무엇으로 정할지(사용자 본인 차량을 A로 할지 등)는 B와 함께 정해야 한다.

### 7.10 `stop_frame`이 `null`이어도 안 멈춘 것은 아닐 수 있다

`stop_frame`은 충돌 후 20프레임 안에 감속이 확인될 때만 값이 생긴다. 충돌 직후 궤적이 끊기면(차가 가려지거나 탐지를 놓침) 감속을 확인할 방법이 없어서 `null`이 된다. cc_150101처럼 충돌 순간 먼지나 파편이 화면을 덮는 사고에서 이런 일이 생긴다. `null`은 "멈추지 않았다"가 아니라 "멈춘 것을 확인하지 못했다"로 읽어야 한다.

### 7.11 기준값은 영상 몇 개로 정했다

`params`의 기준값과 탐지 설정(yolov8s, 입력 640, 추적 문턱 0.15)은 위 영상 세 개로 정했다. 일시정지 기준(0.01/초)도 마찬가지다. 카메라에서 아주 먼 곳에서 천천히 움직이는 차는 화면 속도가 0.01 아래로 나와 멈춘 것으로 잘못 판단될 수 있다.

### 7.13 이어붙이기가 서로 다른 차를 이을 수 있다

`stitch_tracks`는 한 궤적이 끊긴 자리 근처에서 몇 프레임 안에 새로 나타난 궤적을 같은 차로 본다. 충돌 지점처럼 차들이 모이는 곳에서는 사라진 차와 새로 나타난 차가 서로 다를 수 있다. cc_150101에서 북쪽 트럭(66프레임에 사라짐)과 동쪽에서 온 차(71프레임에 0.039 떨어진 곳에 나타남)가 하나로 이어졌다. 한 차는 아래쪽으로, 다른 차는 왼쪽으로 가고 있었다.

그래서 진행 방향 검사를 넣었다(`HEAD_WIN`, `HEAD_MOVE`, `HEAD_MAX`). 앞 조각의 끝 10프레임과 뒤 조각의 처음 10프레임이 둘 다 0.03 이상 움직였고 방향 차이가 100°를 넘으면 다른 차로 보고 잇지 않는다. 기준은 11개 영상의 링크 66개로 정했다.

- 둘 다 움직인 링크 중 같은 차를 이은 것은 방향 차이 2~21°였다(당사자 궤적 포함).
- 라벨로 다른 차임을 확인한 링크는 126°(cc_150101 31←629)와 128°(cc_200914 12←223)였다.
- 공백 동안 회전한 차도 90° 가까이 바뀔 수 있어 100°로 여유를 뒀다.

방향 검사로 막지 못하는 경우가 남아 있다.

- **한쪽이 거의 안 움직이면 검사를 건너뛴다.** 멈춘 차의 박스 떨림으로 방향을 잘못 재지 않기 위해서다. 그런데 충돌 직후의 차는 대개 멈춰 있다. cc_200914에서 이륜차(B)는 충돌 뒤인 78프레임부터만 탐지됐고 거의 움직이지 않아서, 12←223을 끊은 뒤에도 A 차 궤적(12번) 끝에 붙었다.
- 차 종류나 박스 크기로도 가르지 못했다. 같은 차를 바르게 이은 링크에서도 종류가 섞이고(cc_180304 A 궤적은 71프레임 중 19프레임이 이륜차) 박스 면적이 4배까지 변했다(cc_211208 B).

결국 두 당사자가 충돌 지점에서 만나기 전에 각각 탐지되어야 풀린다. AI Hub 프레임 라벨과 맞춰 보는 매칭(`src/eval/match_parties.py`)에서 한 궤적이 A와 B 둘 다에 걸리면 이런 경우로 표시한다.

방향 검사를 넣은 뒤 cc_150101의 B 조각(629번)은 따로 떨어졌지만, 10프레임뿐이라 `finalize_tracks`의 최소 길이(15프레임)에 걸려 버려진다. B가 거의 탐지되지 않은 것이 근본 원인이다.

### 7.12 진입 방위는 화면 기준으로 붙인 이름이다

`entry_from`은 scene.json에 사람이 적은 진입로 `direction`이다. 지도가 없으니 화면 위쪽 진입로를 `north`, 왼쪽을 `west`처럼 화면 기준으로 붙인다. 위에서 내려다본 지도처럼 위·오른쪽·아래·왼쪽이 시계 방향 순서를 지키므로, 좌우 관계(상대가 오른쪽에서 왔는가)와 진입로 기준 진행 방향 판단에는 문제가 없다. 실제 동서남북과는 다를 수 있다.

B 엔진은 `entry_from`이 있으면 방위로 좌우 관계를 판단한다. 다만 2026-10-20 기준으로 B의 변환기(`adapter.py`)가 이 필드를 엔진에 넘기지 않아서, 지금은 `heading_start` 벡터로 판단된다. 변환기의 `OPTIONAL_PARTY_FIELDS`에 `entry_from`을 추가해야 쓰인다. 비신호 교차로 CCTV 18개로 검증하는 작업이 남아 있다. 영상이 늘어나면 기준값이 바뀔 수 있고, 그 경우 `params`에 남은 값으로 어떤 기준이 쓰였는지 확인할 수 있다.
