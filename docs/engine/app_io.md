# 앱 입출력 (`run_app.py`)

앱이 서버에 무엇을 보내고 무엇을 받는지 정리한 문서다. 지금은 서버 없이 `run_app.py` 명령 하나가 서버 역할을 한다. 앱을 만들 때는 아래 입력을 요청 본문으로, `app.json`을 응답으로 보면 된다.

질문 하나하나가 언제 생기고 판정에 어떻게 들어가는지는 `docs/facts_fields.md` 5장에 있다. 이 문서는 앱이 다뤄야 하는 모양만 다룬다.

## 1. 흐름

```
① 영상 + 교차로 네 모서리  ──▶  app.json (status 4가지 중 하나)
                                    │
     needs_answers / no_collision   │  사용자가 답함
                                    ▼
② 영상 + answers.json (지금까지의 답 전부)  ──▶  app.json
                                    │
                  질문이 남으면 ②를 반복, 다 받으면 done
```

YOLO는 ①에서 영상당 한 번만 돈다(10초 영상에 약 18초). ②부터는 저장해 둔 탐지 결과를 다시 읽어서 1초 안에 끝난다. 사용자가 당사자를 박스로 표시했으면 그 당사자를 따라가는 추적(Vit)이 더 붙는다.

## 2. 입력

### 2.1 처음 요청

```bash
python run_app.py data/videos/cc/<영상>.mp4 [--source cctv] --corners "x,y x,y x,y x,y" [--frame-ref 30]
```

| 값 | 뜻 |
|---|---|
| 영상 | CCTV 사고 영상. 압축본이 아닌 원본 해상도 (압축본은 탐지 결과가 달라진다) |
| `--source` | 사용자가 홈 화면에서 고른 영상 종류. `cctv`(기본) / `blackbox`. 앱은 이 선택을 믿는다. `blackbox`면 모서리 없이 바로 `unsupported`(`reason: blackbox_selected`)를 돌려준다. 블랙박스 분석은 아직 없음 |
| `--corners` | 교차로 네 모서리. 화면 크기 기준 0~1 좌표이고 순서는 상관없다. 연석이나 횡단보도 안쪽 끝이 만나는 곳을 누르게 한다. 모서리가 화면 밖이면 화면 끝(0 또는 1)으로 보낸다 |
| `--frame-ref` | 모서리를 찍은 프레임 번호. 기본 0 |
| `--closed` | 삼거리(T자형)면 길이 없는 쪽. `north`/`east`/`south`/`west` (화면 위·오른쪽·아래·왼쪽). 없으면 사거리. 그쪽에는 진입로를 만들지 않고, "어느 쪽 길에서 왔나요?" 질문의 보기에서도 뺀다. 교차로일 때만 |
| `--place` | 장소 종류. `intersection`(기본, 교차로) / `roundabout`(회전교차로) / `parking_lot`(주차장) / `straight`(교차로 아닌 길). 모서리 화면에서 사용자가 고른다. 모서리는 어느 장소든 그 장소의 중심 영역 네 점. 장소에 따라 질문이 달라진다 (3.5) |

네 모서리로 교차로와 네 진입로 영역을 만든다(`src/make_scene.py`). 화면 위쪽 진입로가 `north`, 오른쪽이 `east`다. 실제 방위가 아니라 화면 기준이다.

### 2.2 답 보내기

```bash
python run_app.py data/videos/cc/<영상>.mp4 --answers answers.json
```

모서리는 다시 보내지 않아도 된다. 처음 만든 장면을 결과 폴더에서 다시 쓴다.

`answers.json`에는 **지금까지 받은 답을 전부** 넣는다. 서버는 이전 답을 기억하지 않고 매번 이 파일만 보고 처음부터 다시 계산한다. 직접 표시한 박스(`user_tracks`)도 매번 같이 보낸다.

키는 질문의 `field`, 값은 그 질문의 `options` 중 하나다.

```json
{"parties.1.movement": "straight",
 "road.signal_present": false,
 "road.wider_road": "equal",
 "collision.parties": ["1", "32"]}
```

| `answer_type` | 값 모양 | 예 |
|---|---|---|
| `choice` | `options` 안의 값 하나 (문자열 또는 `true`/`false`) | `"left_turn"`, `false` |
| `pair` | 두 id 배열. `options`가 있으면 그중 하나, `null`이면 `objects`의 id 중 둘 | `["1", "32"]` |
| `frame` | 프레임 번호 (정수). 사용자가 영상을 넘겨 보며 고른 장면 | `96` |
| `boxes` | `user_tracks` 객체 (2.3) | |
| `multi` | `options` 안의 값 목록 (빈 목록 = 해당 없음). 상황이 바뀌어 보기가 달라져도 전에 고른 값은 `all_options` 안이면 받아 줌 | `["emergency:32", "highway"]` |

질문에 `"optional": true`가 붙어 있으면 답하지 않아도 `done`이 된다 (지금은 특수 상황 질문 하나). 결과 화면에 "해당하면 알려 주세요"로 보여 주면 된다.

`questions`에는 아직 답하지 않은 질문만 들어가서, 답한 선택 질문은 빠진다. 결과 화면에서 고른 것을 다시 열어 고치거나 취소하려면 `optional_questions`(답한 것까지 포함한 선택 질문 전부)를 쓰고, 지금 답은 `answers`에서 읽는다 (2026-11-03 추가).

**입력이 잘못되면** 서버는 종료 코드 1과 한국어 안내 한 줄(예: "답을 확인해 주세요: parties.1.movement의 답 'fly'이 보기 [...]에 없어요")을 내고 멈춘다. 이때 `app.json`은 바꾸지 않으니, 앱은 안내를 보여 주고 직전 화면에 머물면 된다. 이렇게 멈추는 경우는 다음과 같다 (`tests/test_inputs.py`에서 확인).

- 보기에 없는 답, 범위 밖이거나 숫자가 아닌 프레임 답
- 이상한 `user_tracks` (박스가 화면 밖, 프레임 범위 밖, 종류 없음, 모양이 틀림)
- 답 파일이 JSON이 아니거나, 없거나, `{}` 모양이 아님
- 모서리가 4개가 아니거나, 숫자가 아니거나, 0~1 밖이거나, 네 점이 한곳에 몰림

부딪힌 쌍을 없는 id나 같은 id 두 번으로 고른 경우는 멈추지 않고 `no_collision`으로 다시 묻는다 (3.4).

### 2.3 당사자 직접 표시 (`user_tracks`)

YOLO가 당사자를 놓쳤을 때(주로 이륜차·자전거) 사용자가 충돌 장면에 박스를 그리고 종류를 고른다.

```json
{"user_tracks": {"9001": {"frame": 129, "bbox": [0.54, 0.38, 0.04, 0.18], "cls": "bicycle"}},
 "collision.parties": ["118", "9001"]}
```

| 값 | 규칙 |
|---|---|
| id | `"9001"`부터 쓴다. 최대 2개 |
| `frame` | 박스를 그린 프레임. 질문 이미지의 `evidence_frame`을 그대로 쓰면 된다. 이 프레임이 충돌 프레임이 된다 |
| `bbox` | `[x, y, w, h]`, 왼쪽 위 기준, 0~1 |
| `cls` | `car`, `truck`, `bus`, `two_wheeler`, `bicycle`, `pedestrian` 중 하나 |

두 당사자를 모두 표시했으면 `collision.parties`는 생략해도 된다. 하나만 표시했으면 상대 id와 함께 `collision.parties`로 보낸다.

표시한 당사자는 추적이 자주 틀려서(정답 박스로 시험했을 때 충돌 전 구간을 맞게 따라간 비율 33~40%) 진행 방향, 온 길, 진입 순서를 다음 응답에서 항상 묻는다.

## 3. 응답 `app.json`

결과 폴더(기본 `outputs/app/<영상 이름>/`)에 생긴다. 이미지 경로는 이 폴더 기준 상대 경로다.

### 3.1 `status`

| `status` | 뜻 | 앱이 할 일 |
|---|---|---|
| `needs_answers` | 판정은 냈지만 확인할 질문이 남음 | 판정 결과를 먼저 보여 주고, 질문은 "확인하면 결과가 바뀔 수 있는 것"으로 보여 준다. 답을 받으면 2.2로 다시 요청 |
| `done` | 질문이 없음 | 판정 결과를 보여 준다 |
| `no_collision` | 충돌을 못 찾았거나, 사용자가 고른 두 객체로 충돌을 만들 수 없음. 판정 없음 | 객체 이미지를 보여 주고 부딪힌 두 객체를 고르게 하거나, 목록에 없는 당사자를 박스로 표시하게 한다 (3.4) |
| `unsupported` | `reason: blackbox_selected`: 사용자가 블랙박스를 고름. `reason: looks_like_blackbox`: CCTV를 골랐는데 카메라가 차와 함께 움직이는 영상으로 보임(안전장치). 흔들리는 CCTV나 CCTV 화면을 휴대폰으로 찍은 영상은 흔들림을 보정해서 분석하므로 해당하지 않음 | `message`의 문구를 보여 준다. `looks_like_blackbox`면 영상 종류를 다시 고르게 한다 |

`done`이어도 판정 모듈이 맞는 도표를 못 찾았을 수 있다. 판정이 나왔는지는 `verdict.status`로 따로 본다 (3.3).

다음 경우에는 `app.json`이 만들어지지 않고 명령이 에러로 끝난다. 앱에서는 "다시 시도" 정도로 처리한다.

- 처음 요청에 모서리가 없거나 4개가 아니거나, 좌표가 0~1 밖
- 답이 보기에 없음, 장면을 고르는 답(`intersection_entry`)이 분석한 프레임 범위 밖
- `user_tracks`의 id·종류·박스가 규칙에 안 맞거나, `frame`이 분석한 프레임 범위 밖 (화면 전환이 있으면 그 앞까지)
- 판정 모듈(`../MTM_B/judge`)이 없음

### 3.2 `needs_answers`, `done` 응답

| 키 | 내용 |
|---|---|
| `video` | 영상 이름 |
| `status` | `needs_answers` / `done` |
| `questions` | 남은 질문 목록 (3.5). `done`이면 빈 배열 |
| `answers` | 이번 요청에 받은 답 (보낸 `answers.json` 그대로) |
| `answer_conflicts` | 사용자 답이 모델 추정값과 다른 질문 목록. 항목마다 `field`, `question`, `model_guess`/`answer`(코드값), `model_choice`/`answer_choice`(한글). 결과 화면에서 "영상 분석과 다르게 입력한 항목"으로 보여 준다 (기획서 6.3, 당사자는 자기에게 유리하게 답할 동기가 있음). 기본값(도로 폭)과 추정값이 없는 질문은 비교하지 않는다. 없으면 빈 배열 |
| `scene_cut` | 영상 중간에 화면 전환(줌인 등)이 있으면 `{"frame", "t"}`. 그 앞까지만 분석했다는 뜻이라 결과에 함께 표시한다. 없으면 `null` |
| `collision` | 충돌 장면. `frame`, `t`(초), 두 당사자 `a`·`b`, `pos`(화면 위치), `confirmed`(`false`면 확정 못 하고 후보를 씀), `image` |
| `verdict` | 판정 요약 (3.3) |
| `issues` | 답에 따라 결과가 갈리는 쟁점 (3.6) |
| `judge_version` | 판정 모듈 버전 |
| `timing_sec` | 단계별 걸린 시간(초) |

### 3.3 `verdict`

| 키 | 내용 |
|---|---|
| `status` | `ok`(도표를 찾아 비율을 냄) / `no_rule`(맞는 도표 없음). `no_rule`이면 `rule_id`와 비율이 `null` |
| `rule_id` | 과실비율 인정기준 도표 번호. 예: `"차12-1(다)"` |
| `title` | 도표 이름 (11-03). 판정 모듈 결과의 `title` 그대로 |
| `fault_by_track` | 당사자 id별 과실(%). 예: `{"32": 70, "1": 30}` |
| `fault_if_pending_by_track` | 속도 보정이 안 돼서 보류한 수정요소까지 적용했을 때의 비율. 보통 `fault_by_track`과 같다 |
| `applied_modifiers` | 적용된 수정요소 이름. 예: `["B 명확한 선진입"]` |
| `unverifiable_factors` | 영상으로는 알 수 없는 수정요소(음주, 휴대전화 등). 항목마다 `label`, `delta`(%p), `question`이 있다. 지금은 답을 받는 길이 없어서 참고용으로만 보여 준다 (5.2의 5번) |
| `assumptions` | 판정 모듈이 사용자 답으로 받은 값 (문장 목록) |
| `provisional` | `true`면 답이 없는 질문을 추정값·기본값으로 채워서 낸 임시 결과 |
| `auto_filled` | 추정값·기본값으로 채운 질문의 `field` 목록 |
| `modifier_details` | 적용된 수정요소마다 `{label, party, track, delta, source, facts}`. `source`가 `user`면 근거 사실 중 하나라도 사용자 답에서 온 것 (운전자 요인, 감산 보기 등). 결과 화면과 투표글에서 "사용자 입력"으로 구분해 보여 준다 (당사자는 자기에게 유리하게 답할 수 있음). `video`면 영상에서 잰 것 (11-02) |
| `auto_facts` | 확신이 높아 질문 없이 영상에서 정한 사실의 `field` 목록 (지금은 신호 색, `MTM_SIGNAL_AUTO_MIN`을 켰을 때만). 결과 화면에 "영상에서 판단한 것"으로 보여 주고 고칠 수 있게 함 |

`fault_by_track`의 키는 YOLO 궤적 id(또는 사용자 표시 id `9001~`)다. 앱에서는 `collision.image`에 같은 id가 그려진 박스로 누가 누구인지 보여 줘야 한다.

`camera_notice` (2026-10-27): 회전·줌하는 CCTV에서 흔들림 보정의 정렬을 확인하지 못한 구간이 있으면 들어간다. 없으면 `null`.

```json
"camera_notice": {"frames": [[94, 149]], "at_collision": true,
                  "message": "부딪힌 장면에서 카메라가 크게 줌하거나 돌아가서, 차의 위치와 진행 방향이 정확하지 않을 수 있어요. 질문의 그림을 보고 직접 확인해 주세요."}
```

`at_collision`이 `true`면 결과 화면에 눈에 띄게 보여 준다. 분석은 그 구간도 그대로 한다 (자르면 정렬이 맞은 사고까지 잘려서).

`corner_notice` (2026-10-28): 찍은 교차로 모서리가 차들이 다닌 곳과 안 맞으면 들어간다. 없으면 `null`. 판정은 그대로 내고, 모서리를 다시 찍어 보라는 안내만 한다 (2.1 처음 요청을 새 모서리로 다시 보냄)

```json
"corner_notice": {"thru_ratio": 0.0, "out_ratio": 0.65,
                  "message": "찍은 교차로 모서리가 차들이 다닌 곳과 잘 맞지 않아요. 모서리를 다시 찍으면 결과가 더 정확해질 수 있어요."}
```

`thru_ratio`는 움직인 차 중 교차로를 지나간 비율(0.1 미만이면 경고), `out_ratio`는 궤적 점 중 교차로·진입로 어디에도 안 든 비율(0.4 초과면 경고). 기준은 모서리 민감도 실험(`docs/archive/experiments_1028.md` 1절)으로 정함

`verdict`에는 인정기준의 장도 들어 있다 (2026-10-26).

| 키 | 내용 |
|---|---|
| `chapter` | 두 당사자 종류로 본 장. `vehicle`(자동차와 자동차, 이륜차 포함) / `bicycle`(자동차와 자전거, 농기계 포함) / `pedestrian`(자동차와 보행자) |
| `chapter_ready` | 그 장의 도표가 판정 모듈에 있는지 (`rules_<장>.json`). 지금은 `vehicle`만 `true` |
| `notice` | `chapter_ready`가 `false`일 때 보여 줄 안내. "'자동차와 자전거(농기계 포함)' 사고 기준은 아직 판정 모듈에 없어서, 이 결과는 자동차끼리의 기준으로 낸 참고값이에요." |

장을 골라 도표를 고르는 일은 판정 모듈이 한다. A는 안내와 질문을 정하는 데만 쓴다 (`src/app/chapters.py`).

### 3.4 `no_collision` 응답

```json
{"video": "cc_3_200303_bike_116_279",
 "status": "no_collision",
 "reason": "not_found",
 "message": "충돌 장면을 찾지 못했어요. 부딪힌 두 당사자를 골라 주세요. 목록에 없으면 화면에 직접 표시해 주세요.",
 "questions": [
  {"field": "collision.parties", "answer_type": "pair", "options": null,
   "objects": [{"id": "1", "cls": "two_wheeler", "first_frame": 48, "last_frame": 149, "in_image": true}],
   "evidence_frame": 106, "image": "frames/objects_f00106.jpg"},
  {"field": "user_tracks", "answer_type": "boxes",
   "options": ["car", "truck", "bus", "two_wheeler", "bicycle", "pedestrian"],
   "max": 2, "id_from": 9001, "evidence_frame": 106, "image": "frames/objects_f00106.jpg"}],
 "answers": {}, "timing_sec": {}}
```

`image`는 움직이는 객체가 가장 많이 보이는 프레임에 객체마다 빨간 박스와 id를 그린 그림이다. `objects`는 움직이는 객체 전부이고, `in_image: false`인 객체는 그림에는 없다(다른 시간에 지나감).

사용자가 할 수 있는 답은 셋이다.

- 목록에서 둘을 고름: `{"collision.parties": ["1", "25"]}`
- 하나는 목록에서, 하나는 직접 표시: `user_tracks` 하나 + `collision.parties`
- 둘 다 직접 표시: `user_tracks` 둘

움직이는 객체가 하나도 없으면 `objects`가 비어 있고, 영상 중간 프레임이 `image`로 온다. 이때는 직접 표시만 가능하다.

`reason`은 이 응답이 나온 이유다. `message`에 사용자에게 보여 줄 문구가 있다.

| `reason` | 언제 | 앱이 할 일 |
|---|---|---|
| `not_found` | 자동으로 충돌을 못 찾음 | 위 세 가지 중 하나로 답을 받는다 |
| `pair_not_together` | 사용자가 고른 두 객체가 같은 화면에 나온 적이 없음 (예: cc_150101에서 트럭은 6~66프레임, 상대 차는 70~88프레임에만 잡힘). 그대로는 충돌 장면을 정할 수 없다 | `image`는 앞 객체가 사라진 때와 뒤 객체가 나타난 때의 가운데 장면이다. 그 장면에서 안 보이는 당사자를 `user_tracks`로 표시하게 한다 |
| `pair_invalid` | 같은 객체를 두 번 골랐거나, 목록에 없는 id를 보냄 | 목록에서 다시 고르게 한다 |

`pair_not_together`, `pair_invalid`일 때는 다음 요청에서 `collision.parties`를 새 답으로 바꿔서 보낸다. 예전 쌍을 그대로 보내면 같은 응답이 다시 온다.

### 3.5 질문 (`questions[]`)

**질문 목록은 서버(A 파이프라인)가 정한다. 앱(FE)은 목록을 코드에 넣지 않는다.** 어떤 질문이 나올지는 앞 답·장소·진행 방향·판정이 갈리는지에 따라 매번 달라서, 서버가 남은 질문만 `questions`로 내려준다. 앱은 `answer_type`별 화면 하나씩만 만들고, 받은 질문을 그대로 그린 뒤 답을 모아 2.2로 다시 보낸다. 새 질문이 생겨도 앱은 고칠 게 없다. 아래 표는 앱 화면 설계와 테스트용 참고다

```json
{"field": "parties.1.movement",
 "question": "1번 차는 어느 방향으로 가고 있나요?",
 "answer_type": "choice",
 "options": ["straight", "left_turn", "right_turn", "u_turn", "unknown"],
 "choices": ["직진", "좌회전", "우회전", "유턴", "모름"],
 "model_guess": "straight",
 "evidence_frame": 63,
 "image": "frames/f00063.jpg"}
```

| 키 | 내용 |
|---|---|
| `field` | 답을 보낼 때 쓰는 키 |
| `question` | 화면에 보여 줄 문장 |
| `answer_type` | `choice`(하나 고르기) / `multi`(여러 개 고르기, 답은 `options` 값의 배열) / `pair`(부딪힌 두 객체) / `frame`(장면 고르기) / `boxes`(직접 박스 표시) (2.2 표) |
| `options` | 보낼 값. `frame`이면 `null` |
| `choices` | `options`와 같은 순서의 한글 표시. 버튼에는 이걸 쓴다 |
| `model_guess` | 모델 추정값. 있으면 그 보기를 미리 골라 둔다. 판정에도 이 값이 들어가 있다 |
| `default` | `true`면 `model_guess`가 추정이 아니라 그냥 기본값이다 (도로 폭, 교차로 안, 특수 상황 등) |
| `optional` | `true`면 답하지 않아도 `status`가 `done`이 될 수 있는 선택 질문 (특수 상황, 바닥 화살표). 결과 화면에서 "해당하면 알려 주세요"로 보여 준다 |
| `group` | 질문 묶음 제목 (`특수 상황`, `운전자 요인`, `신호등`, `도로 표시`). 선택 질문을 앱이 한 화면에 제목별로 모을 때 씀 (11-02) |
| `option_groups` | 특수 상황에만. `options`와 같은 순서로 보기마다 묶음 제목 (`일반`, `회전`, `차로 변경`, `서 있던 차`, `문 열림`, `같은 방향으로 가다가`, `마주 오다가`, `교차로`, `신호`, `이륜차`, `주차장`, `장소·날씨`). 보기가 상황별로 10~20개라 제목별로 나눠 보여 준다 (11-02) |
| `more_options` | 특수 상황에만. `options` 중 이 사건에서 드문 보기 (버스로 잡히지 않은 차의 버스정류장·어린이통학버스, 트럭·버스가 아닌 차의 대형차, 교차로 사고의 주차장·건물 입구 드나들기와 고속도로, 서 있지 않던 차의 문 열림). 앱이 "다른 상황 더 보기" 아래로 접는다. 탐지가 틀릴 수 있어서 빼지는 않고, 골라도 다른 보기와 똑같이 반영된다 (11-04) |
| `all_options` | 특수 상황에만. 답 검사에 쓰는 전체 보기 값 (상황이 바뀌어 보기가 줄어도 전에 고른 답이 에러가 안 나게). 화면에는 `options`만 보여 준다 |
| `depends_on` | 있으면 그 답이 맞을 때만 보이는 질문. 신호 색 질문은 `{"road.signal_present": true}`라서, 신호등이 "있음"이라고 답한 다음 요청부터 나온다 |
| `light_hints` | 신호 색 질문에만. 그 장면에서 모델이 본 신호등 색 `[{"track", "frame", "color", "p"}]` (color는 red/green/etc). 어느 당사자 쪽 신호인지는 모르므로 참고로만 보여 준다 |
| `evidence_frame`, `image` | 질문과 함께 보여 줄 장면. 그림에는 충돌 당사자 `a`(빨강)·`b`(파랑)의 박스와 `#id 종류`가 그려져 있다. 부딪힌 쌍 질문(`pair`)이면 보기에 나온 다른 객체도 초록으로 그린다. 그 프레임에 안 보이는 당사자는 그리지 않는다. 종류는 사용자가 답했으면 답한 값으로 쓴다. **진행 방향·어느 길에서 왔는지 질문**은 그림이 다르다 (`frames/path_<id>.jpg`): 진입로마다 색을 칠하고 보기 이름("화면 위쪽 길" 등)을 적은 뒤, 그 당사자가 지나간 길을 선과 화살표로 그린다. 보기가 화면 기준 방위라 길이 대각선이면 어느 길이 "위쪽 길"인지 그림 없이는 알 수 없어서다 |

질문은 아래 표의 것들이고, 한 사고에 다 나오지는 않는다 (보통 3~8개). 보행자·자전거 질문 2가지는 그 장 도표가 판정 모듈에 생겨야 나온다. 종류 보기의 농기계(`farm_machine`)는 탐지로는 못 잡아서(AI Hub 라벨에 없음) 사용자가 고르거나 직접 표시할 때만 들어온다. **결과 화면에서 당사자 종류를 언제든 고칠 수 있게** 해 두는 게 좋다. 종류가 확실해 보여서 질문이 안 떠도 경운기가 트럭으로 잡힐 수 있고, 종류에 따라 인정기준의 장이 바뀐다.

| `parties.<id>.emergency_mode` | 긴급자동차가 달린 방식 (특수 상황에서 긴급자동차를 고름) | 보통 / 도로 가운데·왼쪽 / 앞차를 앞지르던 중 |
| `road.location` | 부딪힌 곳 (충돌이 교차로 영역 밖일 때) | 교차로 안 / 교차로를 벗어난 길 (기본값 교차로 안) |
| `parties.<id>.lane_change_dir` | 차로를 바꾼 방향 (진로 변경 당사자) | 왼쪽 / 오른쪽 |
| `parties.<id>.overtake_type` | 앞지르기 방법 (특수 상황에서 앞지르기를 고른 당사자) | 7가지 (노란 실선, 오른쪽 파고들기 등) |
| `pair.u_turn_timing` | 두 차 다 유턴일 때 | 뒤차가 갑자기 / 거의 같이 |
| `parties.<id>.ped_signal_green_at_turn` | 우회전 때 보행자 신호 (신호 교차로) | 초록이었음 / 아니었음 |
| `parties.<id>.lane_marking` | 있던 차로의 바닥 화살표 (교차로, 선택 질문) | 좌회전만 / 직진·좌회전 / 직진만 / 직진·우회전 / 우회전만 / 없음·모름 |
| `road.center_line_rule_not_applied` | 좁은 길 교행 (마주 오는 사고 + 중앙선 있음) | 그런 길 / 아님 |
| `parties.<id>.crossing_place` | 부딪힌 곳 (보행자·자전거·농기계 당사자, 그 장 도표가 판정 모듈에 있을 때만) | 횡단보도 위 / 횡단보도 부근 / 횡단보도 없는 차도 / 보도·길 가장자리 |
| `parties.<id>.ped_signal_at_crossing` | 보행자 신호 색 (신호등 있음 + 횡단보도 위·부근일 때만) | 초록 / 초록 점멸 / 빨강 |
| `collision.parties` | 부딪힌 두 객체 | 쌍 목록 (`pair`). "충돌 뒤 탐지"가 붙은 쌍도 있다 |
| `intersection_entry_order` | 누가 먼저 들어갔는지 | 당사자 a / 당사자 b / 동시 |
| `road.signal_present` | 신호등이 있는지 (교차로면 늘) | 있음 / 없음 |
| `parties.<id>.signal_at_entry` | 교차로에 들어갈 때 이 차 쪽 신호 색 (신호등 있음이라고 답했을 때) | 신호 색 보기 (`light_hints` 참고) |
| `parties.<id>.signal_at_collision` | 부딪힐 때 신호 색 (진입 뒤 화면 신호가 바뀌었을 때만) | 신호 색 보기 |
| `road.center_line` | 중앙선이 있는지 (교차로, 또는 장소가 교차로 아닌 길) | 있음 / 없음 (골목길) |
| `road.wider_road` | 어느 도로가 넓은지 | 폭이 비슷함 / 화면 위아래 도로 / 화면 좌우 도로 |

`<id>`는 당사자 궤적 id다. 사용자가 `collision.parties`를 다른 쌍으로 고르면 당사자가 바뀌므로, 다음 응답의 질문 `field`도 새 id로 바뀐다. 앱은 질문 목록을 매번 응답에서 새로 받아야 하고, 이전 당사자에 대한 답은 버려야 한다. 남겨 보내도 에러는 나지 않지만, 이번 사고와 상관없는 궤적의 값이 판정 모듈에 같이 넘어간다.

### 3.6 쟁점 (`issues[]`)

도로 폭은 화면으로 추정할 방법을 못 찾아서(시도한 방법은 `docs/A_pipeline.md` 참고) 답이 없으면 세 경우로 각각 판정한다. 세 결과가 같으면 도로 폭 질문을 지우고, 다르면 쟁점으로 넣는다.

중앙선(`road.center_line`)도 같은 방법을 쓴다 (2026-10-26). 답이 없으면 있음·없음으로 각각 판정해 보고, 둘 다 지금 판정과 같으면 질문을 지운다. 둘이 다르면 질문을 남기고 쟁점으로도 넣는다. 평가 영상 29개에서 중앙선 질문이 29개 → 2개로 줄었고 판정은 하나도 바뀌지 않았다.

```json
"issues": [
 {"field": "road.wider_road",
  "question": "교차하는 두 도로 중 어느 쪽이 더 넓은가요?",
  "cases": [
   {"answer": "equal", "choice": "폭이 비슷함", "rule_id": "차12-1(다)", "fault_by_track": {"32": 70, "1": 30}},
   {"answer": "north_south", "choice": "화면 위아래로 지나는 도로", "rule_id": "차12-2(나)", "fault_by_track": {"1": 20, "32": 80}},
   {"answer": "east_west", "choice": "화면 좌우로 지나는 도로", "rule_id": "차12-2(다)", "fault_by_track": {"32": 60, "1": 40}}]}]
```

(cc_3_211208, 답 없이 돌린 결과. 정답은 "폭이 비슷함"의 30 : 70)

같은 사고인데 도로 폭 답 하나로 도표가 셋으로 갈리고, 1번 과실이 20%에서 40%까지 바뀐다. 그래서 `verdict`의 결과(기본값 "비슷함")만 보여 주지 말고, 경우별 결과를 나란히 보여 주고 사용자가 고르게 한다. 고른 경우의 `answer`를 `road.wider_road` 답으로 보내면 된다. 쟁점이 있는 동안 같은 `field`의 질문도 `questions`에 남아 있으니, 둘 중 한 곳에서만 묻는다.

앱에는 `app.json`과 이미지만 넘기면 된다. 나머지는 확인용이다.

| 파일 | 내용 |

## 5. 와이어프레임과 맞춰 본 결과 (2026-10-22)

`MTM_와이어프레임.pdf`(아직 레포에 없음)의 화면 9개를 지금 `app.json`과 맞춰 봤다. 와이어프레임 예시는 sample.mp4(22번 차량 ↔ 28번 이륜차, 차14-1 70 : 30)다.

### 5.1 화면별로 필요한 값

### 5.2 A가 `app.json`에 더할 것

1. (완료, 2026-10-24) 질문·충돌 근거 이미지에 당사자 박스와 id를 그린다. 질문이 "22번 차량"이라고 부르는데 그림에 번호가 없으면 사용자가 누군지 모른다.
2. `verdict`에 `result.json`의 값을 옮긴다: 도표 제목(`title`), 출처(`source.ref`), 역할(`roles`, A·B가 어느 궤적인지), 계산 과정, 보정 대기(`pending_calibration`), 적용하지 않은 수정요소와 이유, 관련 법규, 주의 문구(`disclaimer`).
3. 당사자 요약(`parties`): id별 종류, 진행 방향, 들어온 길. 결과 화면의 "22번 차량 · 우회전"에 쓴다.
4. 사건 기록: 진입, 충돌, 정지 시각. facts의 `events`와 `intersection_entry`에서 뽑는다.
5. 수정요소 답: `parties.<id>.user_factors`(배열)로 받아 B의 당사자별 `user_factors`로 넘긴다. B 쪽 값 이름(`phone`, `drunk_under_0.03` 등, FACTS_SPEC)과 `unverifiable_factors`의 id(`A:phone_use`, `A:drunk_under_003`)가 달라서 대응표가 필요하다. `unverifiable_factors`의 `party`는 역할(A·B)이라 2번의 `roles`로 궤적 id를 찾아야 한다.
6. 진행 상황: 단계가 끝날 때마다 결과 폴더에 `progress.json`을 쓴다. 와이어프레임의 네 단계는 `camera`·`tracks`(객체 탐지), `stitch`~`collision`(추적·충돌 분석), `zones`~`judge`(과실 판정)로 나누면 된다.
7. 근거 영상: `render_tracks.py`를 선택 단계로 붙인다. 영상 길이만큼 다시 그려야 해서 요청할 때만 만든다.

### 5.3 와이어프레임에서 맞출 것

- **교차로 네 모서리를 누르는 단계**가 있어야 한다. 장면 설정의 첫 프레임 그림에서 누르게 하고, 누른 뒤 영역을 겹쳐 보여 주면 된다.
- **두 도로의 폭**은 "다름"만으로는 판정할 수 없다. 어느 쪽이 넓은지가 필요해서 보기를 "같음 / 화면 위아래 길이 넓음 / 화면 좌우 길이 넓음 / 모름"으로 바꿔야 한다. "모름"이면 판정 결과 화면에 경우별 결과(3.6)를 보여 주는 칸이 필요하다.
- **중앙선 유무**를 장면 설정에 넣는 걸 제안한다. 190510처럼 중앙선 답 하나로 도표가 바뀐다.
- **장소 유형**의 직선 도로·주차장 출입구는 아직 처리하지 못한다. 네 모서리로 교차로와 진입로를 만드는 방식이라 교차로만 된다. **삼거리**는 2026-10-24부터 된다. 장면 설정에서 삼거리를 고르면 길이 없는 쪽(위·오른쪽·아래·왼쪽)도 같이 받아 `--closed`로 넘긴다 (2.1).
- 장면 설정 답은 처음 요청에 같이 보내면 된다. 키는 `road.signal_present`, `road.wider_road`, `road.center_line`이다.
  ```bash
  python run_app.py <영상> --corners "x,y x,y x,y x,y" --answers scene_answers.json
  ```
- 현저한 과실 보기가 3개(전방주시, 음주, 휴대전화)인데 B 판정 모듈에는 2개가 더 있다(시속 20km 미만 속도 위반, 짙은 썬팅). 속도 위반은 사용자가 답하기 어려우니 빼도 되고, 썬팅은 넣는 게 맞다.

## 6. 아직 정하지 않은 것

- 서버 형태(HTTP API, 작업 큐 등). 처음 요청은 18초 넘게 걸리므로 바로 응답하기보다 작업을 맡기고 결과를 받아 가는 방식이 맞을 것 같다. 와이어프레임의 "백그라운드에서 계속" 버튼도 이 방식을 전제로 한다.
- 중앙선 질문도 도로 폭처럼 쟁점으로 보여 줄지 (B에게 물어봄).
