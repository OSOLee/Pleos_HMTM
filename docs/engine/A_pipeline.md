# CCTV 교통사고 과실비율 분석 — A 파트 (영상 분석)

CCTV 사고 영상과 장면 정의(scene.json)를 입력받아 사고 사실을 정리한 `facts.json`을 만든다.
facts.json은 B 파트 규칙 엔진(rules.json → result.json)의 입력이다.

## 파이프라인

```
영상 + scenes/*.json
 → camera_check      카메라 고정/이동 판단, 이동 카메라면 중단             → camera.json
 → track_video       YOLO 탐지 + ByteTrack 추적 + 화면 전환(줌인 등) 감지 → tracks.json
 → stitch_tracks     끊긴 ID 이어붙이기 (공백·거리·진행 방향·신호등 구분) → tracks_stitched.json
 → finalize_tracks   클래스 확정, 정지/이동 판정, 빈 프레임 보간      → tracks_final.json
 → detect_collision  접촉 + 직후 속도 급감으로 충돌 확정, 못 하면 후보   → collision.json
 → zone_events       영역 타임라인, 교차로 진입·나간 진입로·일시정지   → zones.json
 → build_facts       당사자 사실 정리, 확인 질문(unknowns) 생성         → facts.json
```

무거운 YOLO는 첫 단계에서 한 번만 돌리고, 이후 단계는 JSON만 읽는다.

### 탐지 설정

`track_video.py` 맨 위 상수로 정한다.

| 상수 | 값 | 이유 |
|---|---|---|
| `MODEL` | `yolov8s.pt` | yolov8n보다 야간·원거리 차량을 더 잘 잡는다 |
| `IMGSZ` | `640` | 1280은 카메라 가까이 온 큰 차(cc_200303의 SUV, cc_150101의 트럭)를 놓쳤다 |
| `TRACKER` | `src/analyze/bytetrack_low.yaml` | 기본 ByteTrack은 신뢰도 0.25 이상만 새 궤적으로 받는다. CCTV 당사자는 0.1~0.25로 잡히는 경우가 많아 0.15로 낮췄다 |

sample, cc_150101, cc_200303 세 영상에서 yolov8n·yolov8s, 입력 640·1280, 추적 문턱 기본·낮춤을 비교해 정했다.

#### 추적기가 버린 탐지 이어 붙이기 (`LEFT_*`)

이륜차·자전거 당사자 라벨 프레임에서 단계별로 세어 보니, 탐지(640) 103장 → 추적 43장 → 최종 49장이었다(3프레임마다 하나, 238장 기준). 탐지가 아니라 **추적에서 절반 넘게 사라진다.** ByteTrack은 새 물체를 다음 프레임에도 잡혀야 궤적으로 확정하는데, 이륜차·자전거는 한 프레임씩 끊겨 잡혀서 확정 전에 버려진다. 입력을 1280으로 키우는 것(문턱 0.05에서 52%, 시간 3배)보다 이게 컸다.

그래서 탐지(`model.predict`)와 추적(`BYTETracker.update`)을 따로 부른다. 추적기가 쓰지 않았고 어떤 궤적과도 겹치지 않는(IoU < 0.3) 탐지를 모아, 8프레임 안에 가까이(1프레임당 0.05, 공백이 길면 √공백 배) 비슷한 크기로 다시 잡히면 같은 조각으로 잇는다. 탐지 3개 이상인 조각만 남기고, 빈 프레임은 선형으로 채운다. 조각 id는 100000부터다. YOLO는 그대로 프레임당 한 번 돈다.

조각은 잡음(주차 차, 행인의 깜빡이는 탐지)이 많아서 다음처럼 따로 다룬다.

- 이어붙이기(`stitch_tracks`)에서 추적기 궤적과 잇지 않는다. 이었더니 멈춘 차 궤적이 "움직이는 궤적"이 되어 가짜 충돌이 크게 늘었다(cc_200511: 주차 차끼리 확정 충돌 6개).
- 충돌 선택(`detect_collision`)에서 추적기 궤적끼리의 충돌을 먼저 고르고, 조각이 낀 충돌은 그게 없을 때만 쓴다. 질문 보기에는 들어간다.
- 보행자끼리의 충돌은 아예 보지 않는다.

이 방식으로 이륜차·자전거 라벨 프레임을 잡는 비율이 18% → 46%가 됐고(조각 포함), 사용자 입력 없는 당사자 일치가 2/11 → 3/11이 됐다(cc_200303 자전거). cc_180629는 정답 쌍이 질문 보기에 들어갔다.

#### 화면 전환

화면 전환(줌인 등)은 프레임을 32×18로 줄여 이전 프레임과의 평균 밝기 차이가 10을 넘으면 그 지점에서 분석을 멈춘다(`SCENE_SIZE`, `SCENE_THRESH`). 처음에는 320×180에서 6이었는데, 재인코딩 영상의 주기적인 화질 변화(cc_200511, 최대 10.1)와 빗속 야간 화면(cc_200914)을 화면 전환으로 잘못 봐서 분석이 16프레임, 92프레임에서 멈췄다. 32×18로 줄이면 이런 잔변화는 6 아래로 내려가고, 진짜 화면 전환은 15 이상으로 남는다.

### 판정까지 돌린 결과 (2026-10-21)

`run_app.py`로 11개를 두 가지로 돌렸다. 결과표는 `tools/evaluate/results_table.py <결과 폴더>`로 만든다(교차로 모서리는 `scenes/cc_<날짜>_corners.json`).

- **자동** (`outputs/eval_auto`): 사용자 입력 없이 추정값·기본값으로 판정
- **답 반영** (`outputs/eval_tap`, 넣은 답은 영상마다 `answers.json`): 근거 장면을 보고 질문에 답하고, YOLO가 놓친 당사자는 박스로 표시

### 평가 영상 24개로 늘린 결과 (2026-10-24, 자동만)

1차 범위(비신호 사거리·T자형)의 평가 사고를 11개에서 24개로 늘렸다 (`splits/cctv_split.json`의 평가 사고 중 1차 범위, 기준 영상). 새 13개는 비신호 사거리 4개, T자형 9개다. 모서리는 격자와 정답 경로를 보고 정했고(`scenes/cc_<날짜>_corners.json`), T자형은 길 없는 쪽을 함께 정했다. 처음 14개였는데 190201이 180420의 복사본(보랏빛 색 변경, 시간 밀림)이라 묶고 뺐다. 이 쌍은 중복 확인 도구가 놓쳤다(지문 0, 움직임 0.71). 후보 기준을 0.65로 낮춰 다시 찾고, 학습↔평가·범위 내 평가끼리인 사고 쌍 39개를 그림으로 확인했지만 더 없었다.

| 결과 | 영상 수 | 영상 |
|---|---|---|
| 이동 카메라로 판정돼 분석 안 함 (`unsupported`) | 7 | 160316, 180420, 190106, 191207, 200507, 200520, 200711 |
| 분석함 | 17 | 기존 11개 + 200212, 200702, 210224, 210814, 211119, 211217 |

- 이동 카메라 7개는 판정이 틀린 게 아니다. 배경 흐름 중앙값이 0.6~1.3픽셀로, 고정 CCTV(0.01~0.13)와 확실히 다르다. 모니터 화면을 휴대폰으로 다시 찍었거나(200507, 160316, 190106) 흔들리고 확대된 영상이다. 기획서에서 2차로 미룬 "스마트폰 재촬영"이다. 지금 파이프라인은 교차로 영역을 고정해 두므로 분석할 수 없다. AI Hub 라벨로 CCTV라고 해서 고정 카메라는 아니다.
- 자동 결과: 당사자 일치 3/24, 비율 일치 1/24 (`outputs/결과표_자동.md`). 새로 분석한 6개는 모두 당사자 불일치다.
- **새 6개는 탐지가 아니라 충돌 고르기에서 틀렸다.** 대부분 차대차라 두 당사자를 잘 잡았는데(예: 200212 A 124/124, B 101/117 프레임), 고른 충돌 쌍이 틀렸고 "부딪힌 두 객체" 질문의 보기에도 정답 쌍이 없었다. 기존 11개는 이륜차·자전거 탐지가 주원인이었지만, 차대차에서는 충돌 고르기가 따로 문제다.
- 그래서 충돌 접촉 기준과 순위를 바꿨다(`facts_fields.md` 7.1). 바꾼 뒤 자동 결과는 **당사자 일치 7/24**(전 3/24), 비율 일치 1/24. 분석한 17개 중 자동으로 맞히거나 질문 보기에 정답이 든 영상은 11개다. 답 반영 결과(당사자 11/11, 비율 4/11)는 그대로다. 당사자가 맞은 210224·211217은 판정까지 갔지만 비율이 틀렸다(답 없이 기본값으로 판정).

### 흔들리는 CCTV 보정 (2026-10-26)

예전에는 카메라가 움직이면 블랙박스로 보고 분석하지 않았다. 그런데 평가 영상에서 걸린 9개(신호 보행자 2개 포함)는 모두 **CCTV 화면을 휴대폰으로 찍었거나 흔들리는 CCTV**였다. 앱 안내 문구("블랙박스 영상으로 보여요")도 틀렸다.

| 영상 | 첫 프레임과 맞는 특징점 (중앙값) |
|---|---|
| 고정 CCTV | 1,533 |
| 움직이는 CCTV | 69~947 |
| 블랙박스 | 9~12 |

흔들리는 CCTV는 같은 장면이 흔들리기만 해서 첫 프레임과 계속 맞고, 블랙박스는 앞으로 달려 금방 다른 장면이 된다. 그래서 `camera_check`가 움직이는 카메라로 보면 `src/analyze/stabilize.py`로 먼저 보정을 시도한다.

- `check()`: 앞 60프레임에서 첫 프레임과 맞는 점 중앙값이 50 이상이면 보정할 수 있음. 아니면 `unsupported` (문구: "카메라가 차와 함께 움직이는 영상(블랙박스)…")
- `run()`: 프레임마다 ORB 특징점을 첫 프레임과 맞춰 호모그래피로 되돌린 `stabilized.mp4`를 만들고, 그 뒤 모든 단계가 이 영상을 쓴다. 프레임별 변환은 `stabilize.json`에 남김
- 평가할 때는 정답 라벨 박스를 같은 변환으로 옮겨 비교한다 (`src/eval/match_parties.align_gt`)
- 보정 뒤 화면 이동: 190106 147→15픽셀, 200507 94→8픽셀
- 틀린 변환 거르기 (`JUMP_MAX` 0.1): 충돌 뒤 큰 차가 카메라 앞을 가리면 맞는 점이 차에 몰려 변환이 크게 틀어진다(160726 120~124프레임이 검은 화면, 171218은 100프레임부터 화면이 기울어짐). 앞 프레임 변환과 비교해 화면 귀퉁이가 작업 폭의 10%보다 많이 움직이면 버리고 앞 프레임 변환을 이어 쓴다. 평가 영상 7개는 190106·200520에서 한 프레임씩만 바뀜
- 모서리 찍기(`tools/pick_corners.py`)도 결과 폴더에 보정 영상이 있으면 그걸 보여 준다. 보정 영상은 첫 프레임에 맞춰져 있어 좌표가 원본 첫 프레임과 같다

같이 고친 화면 전환 검사 (`track_video.py`)

- 검은 테두리는 빼고 비교 (보정한 영상은 테두리가 매 프레임 움직여 전환으로 잡혔음)
- 화면이 튀면 바로 멈추지 않고 3프레임(`GLITCH_MAX`)까지 기다려, 튀기 전 장면으로 돌아오면(기준의 1.5배 안) 잡음으로 보고 그 프레임만 건너뜀 (`glitch_frames`). 200520은 휴대폰 촬영이 한 프레임 뿌옇게 튀었고, **190510은 153~156프레임이 충돌 순간의 초록 섬광이었는데 예전에는 여기서 "화면 전환"으로 분석을 멈췄다** (영상은 299프레임까지 같은 장면). 이제 끝까지 분석함

#### 회전·줌하는 CCTV (2026-10-27)

- 어긋난 곳에서 분석을 자르려 했지만, 크게 줌한 화면은 정렬이 맞아도 첫 화면과 특징점이 거의 안 맞아서 맞았는지 틀렸는지 가를 수 없었다 (171218은 맞았는데 점수 0, 220103은 어긋났는데 0). 자르면 171218의 충돌(111프레임)까지 잘린다

### 신호등 색 분류기 (2026-10-25, 파이프라인 연결 전)

B 판정 모듈은 당사자별 `signal_at_entry`, `signal_at_collision`(green / yellow / red 등)을 원한다. 지금 파이프라인은 신호등이 보이는지만 보고 색은 보지 않는다. 먼저 색 분류기를 만들었다.

- 데이터: CCTV 신호등 라벨은 빨강 777, 기타 102뿐이고 초록이 없어서, 블랙박스 영상 183개를 받아(`data/videos/bb_lights`, 압축 파일 4개 약 3GB) 라벨 박스를 잘랐다 (`src/dataset/light_crops.py` → `outputs/lights`, 26,281장). 학습·검증·시험은 영상 단위로 7 : 1.5 : 1.5
- 라벨은 red / green / etc. **etc는 노랑, 꺼진 등, 뒷면, 빨강+화살표, 흐릿한 덩어리가 섞인 "기타"**라 하나의 색으로 맞힐 수 없다
- HSV 규칙(`src/analyze/light_color.py`): 켜진 등 가운데가 하얗게 날아가 "꺼짐"으로 보는 경우가 많아, 학습 세트로 기준값을 찾아도 66%가 한계
- 작은 CNN(`src/analyze/light_cnn.py`, 가중치 `models/light_cnn.pt`, CPU 몇 분): 시험 세트 정확도 0.70. 빨강 재현율 0.85, 초록 0.93, etc 0.27

| 시험 세트, 확률 기준 | 빨강 정밀도 / 잡은 비율 | 초록 정밀도 / 잡은 비율 |
|---|---|---|
| ≥ 0.5 | 0.68 / 0.83 | 0.72 / 0.92 |
| ≥ 0.8 | 0.76 / 0.59 | 0.83 / 0.84 |
| ≥ 0.9 | 0.73 / 0.37 | 0.90 / 0.78 |

- 틀리는 것은 대부분 etc를 빨강·초록으로 본 경우다. 검증과 시험의 숫자 차이가 커서(빨강 정밀도 0.85 대 0.68) 영상 수가 더 있어야 안정적으로 잴 수 있다
- CCTV 신호등 라벨(영상 6개, 874개)에서 빨강의 87%를 빨강으로 봤다 (초록 라벨은 없음)
- **그래서 이 결과로 신호 색을 확정하지 않는다.** 신호 색은 판정을 뒤집는 값이라(기획서 6.3), 모델 값은 질문의 추정값(`model_guess`)으로만 쓰고 사용자에게 확인받는 방향으로 연결할 것이다. 노랑은 따로 라벨이 없어서 지금 모델은 노랑을 내지 못한다

### 신호 색 질문 연결 (2026-10-25)

- `src/analyze/light_states.py`(새 단계, `run_app`에서 facts 전에): 신호등 궤적마다 3프레임 간격으로 색을 기록 → `lights.json`, facts의 `traffic_light_states`
- 교차로면 "신호등이 있나요?"를 항상 묻는다. 예전에는 신호등이 하나도 안 잡히면 "없음"으로 확정했는데, CCTV는 신호등이 작거나 화면 밖인 경우가 많다(cc_210819는 신호 교차로인데 진짜 신호등을 못 잡고 화면 구석 물체를 신호등으로 잡음). 답이 없으면 추정값 "없음"으로 판정하므로 평가 결과는 그대로다
- "있음"으로 답하면 당사자별 신호 색 질문(진입 때, 화면 신호 색이 바뀌었으면 충돌 때도)이 나온다. 추정값은 넣지 않고, 그 장면의 신호등 색을 `light_hints`와 그림의 이름표로 참고만 하게 한다. 답은 B의 `signal_at_entry`, `signal_at_collision`으로 넘어간다
- 확인: 평가 41개 판정 그대로(신호등이 안 잡힌 7개에 신호등 질문만 늘어남). cc_210819로 질문 → 답 → B에 넘어가는 것까지 확인. 판정은 진행 방향 등 다른 답이 없어 아직 안 나옴
- 비신호 교차로에서도 신호등 궤적이 많이 잡히는데 대부분 "빨강"이다. 자동차 미등이나 간판을 신호등으로 잡은 것으로 보인다. 그래서 신호등이 잡혔다는 것만으로 신호 교차로라고 보지 않는다

### CCTV 중복 확인과 학습·평가 나누기 (2026-10-23)

탐지 모델 재학습(B 담당)에 평가 영상이 섞이지 않게, AI Hub CCTV 132개를 사고 단위로 학습·예비·평가로 나눴다. 결과는 `splits/cctv_split.json`(코드용), `splits/cctv_split.md`(사람용)다.

같은 사고가 이름만 다른 파일로 여러 번 들어 있다(색 변경, 검은 테두리, 어안 효과, 모니터 재촬영). 라벨 값으로는 묶을 수 없어서(같은 영상에 다른 라벨, 같은 라벨에 다른 사고) 영상 자체를 비교했다.

1. `tools/data/find_duplicates.py data/videos/cc`: 두 가지로 후보를 찾는다. 0.5초 간격 프레임의 흑백 지문(dHash)이 얼마나 겹치는지(`share`), 프레임 사이 밝기 변화를 시간 순으로 늘어놓은 움직임 곡선의 상관(`motion_corr`). 지문만으로는 색을 바꾸거나 테두리를 붙인 복사본을 놓쳤다(cc_3_190506 묶음 4개 중 2개).
2. 후보 153쌍을 그림으로 모두 확인해 `outputs/dedup/groups.json`(같은 사고 44묶음)을 만들었다. 확인 결과 기준은 이렇다.
   - 지문 0.5 이상이고 움직임 0.75 이상, 또는 움직임 0.93 이상: 같은 사고 (73쌍 모두)
   - 지문만 높고 움직임 0.6 안팎: 같은 카메라에서 찍힌 다른 사고 (12쌍)
   - 움직임만 0.8~0.93: 다른 장면 (이미 묶인 쌍 제외)
3. `tools/data/make_split.py outputs/dedup/groups.json`: 규칙대로 나눈다 (파일 맨 위 설명). 132개 = 사고 76개 → 학습 14, 예비 2, 평가 60. 차대차 직선도로 2개는 원본 압축 파일이 46GB라 받지 않고 평가로 뒀다.

지금 평가 11개에도 복사본이 있었다(150101 ↔ 161103, 211208 ↔ 170203·180518·220504, 200511 ↔ 200222). 1차 범위(비신호 사거리·T자형)에서 평가에 쓸 수 있는 사고는 25개다.

같은 사고의 복사본끼리 과실비율 라벨이 다른 경우가 있어서, 사고마다 기준 영상을 정하고 그 라벨을 정답으로 쓴다. 복사본의 A·B가 기준 영상과 반대로 붙은 경우(211208 묶음)는 프레임 라벨의 종류, 나타난 순서, 박스 위치 순으로 맞춘다. 맞춰도 비율이 다른 사고 5개는 `splits/cctv_split.md` 맨 아래에 있다.

```
data/videos/        입력 영상 (git 제외, AI Hub 원본)
outputs/            결과 JSON·영상 (git 제외)
```

### 앱 프로토타입 (`run_app.py`)

앱이 서버에 요청하는 흐름을 명령으로 흉내 낸다. B 판정 모듈이 필요하므로 `feature/B`를 옆 폴더에 받아 둔다. A 브랜치에는 섞지 않는다.


사용자가 표시한 당사자를 따라가는 Vit 추적기 모델(약 0.7MB)도 처음 한 번 받는다. 없으면 MIL 추적기로 대신하지만 훨씬 느리고(영상당 약 10초) 엉뚱한 물체에 붙기 쉽다.

```bash
mkdir -p models && curl -sSL -o models/object_tracking_vittrack_2023sep.onnx https://media.githubusercontent.com/media/opencv/opencv_zoo/main/models/object_tracking_vittrack/object_tracking_vittrack_2023sep.onnx
```

```bash
# 1) 처음: 영상 + 교차로 네 모서리 → 질문 목록
python run_app.py data/videos/cc/<영상>.mp4 --corners "x,y x,y x,y x,y"

# 2) 답 반영: YOLO는 다시 돌리지 않고 이어붙이기부터 다시 → 판정
python run_app.py data/videos/cc/<영상>.mp4 --answers answers.json
```

결과는 `outputs/app/<영상 이름>/`에 생긴다. 앱이 주고받는 값(입력, `app.json` 상태별 모양, 질문, 쟁점, `user_tracks`)은 `docs/app_io.md`에 정리했다.

| 파일 | 내용 |
|---|---|
| `app.json` | 앱에 넘길 응답: `status`, 남은 질문(근거 이미지 경로 포함), 판정 요약, 단계별 시간 |
| `result.json` | B 판정 결과 전체 |
| `facts.json` | 사실 |
| `facts_judge.json` | 판정에 실제로 넘긴 사실 (답이 없는 질문을 추정값·기본값으로 채운 사본) |

`app.json`의 `issues`는 **쟁점**이다. 도로 폭은 화면으로 추정하지 못해서(변 길이, 차 크기, 교통량, 도로 표시 모두 시험했지만 실패. 무료 비전 모델 Florence-2-base도 시험했는데, 횡단보도를 화면 전체 박스로 찾고 진입로 설명은 장면과 상관없는 내용을 지어냈으며 한 장에 15초 이상 걸렸다), 답이 없으면 세 경우(비슷함 / 위아래 길이 넓음 / 좌우 길이 넓음)로 각각 판정한다. 결과가 모두 같으면 도로 폭 질문을 지우고, 다르면 경우별 도표와 비율을 `issues[].cases`에 넣는다. cc_200914·cc_200822는 기본 결과(비슷함)는 정답과 다르지만, 정답 비율이 쟁점 안에 들어 있다.
| `frames/f00078.jpg` | 질문과 충돌 장면의 근거 프레임 |

| `status` | 뜻 | 앱이 할 일 |
|---|---|---|
| `needs_answers` | 질문이 남아 있음. 판정은 추정값·기본값으로 이미 냄 (`verdict.provisional: true`, 채운 질문은 `verdict.auto_filled`) | 추정 결과를 먼저 보여 주고, 질문은 "확인하면 바뀔 수 있는 쟁점"으로 보여 줌. 답을 받으면 `--answers`로 다시 실행 |
| `done` | 질문을 다 받음 | 판정 결과 표시 |
| `no_collision` | 충돌을 못 찾음. 움직이는 객체를 한 장면에 id와 함께 그린 이미지(`frames/objects_f*.jpg`)와 객체 목록을 줌 | 사용자가 목록에서 두 객체를 고르면 `collision.parties`, 목록에 없는 당사자는 화면에 박스를 그리고 종류를 골라 `user_tracks`로 넘김 |
| `unsupported` | 이동 카메라(블랙박스) | CCTV만 지원한다고 안내 |

`answers.json`은 질문의 `field`를 키로 쓴다. 값은 `options`에 있는 코드값이다.

```json
{"parties.1.movement": "straight", "road.signal_present": false,
 "road.wider_road": "equal", "collision.parties": ["1", "32"]}
```

YOLO가 놓친 당사자를 직접 표시할 때는 `user_tracks`에 박스를 넣는다. id는 9001부터 쓰고, 박스는 충돌 장면(질문 이미지의 프레임)에서 그린다. 그 프레임이 충돌 프레임이 된다. 두 당사자를 모두 표시하면 `collision.parties`는 생략해도 된다.

```json
{"user_tracks": {"9001": {"frame": 129, "bbox": [0.54, 0.38, 0.04, 0.18], "cls": "bicycle"}},
 "collision.parties": ["118", "9001"]}
```

표시한 당사자는 진행 방향, 온 길, 진입 순서를 항상 다시 묻는다 (`docs/facts_fields.md` 5장).

단계 하나만 다시 돌릴 때 (루트에서 실행):

```bash

python src/analyze/zone_events.py scenes/sample.json
```

확인 도구 (루트에서 실행):

```bash
python tools/evaluate/render_tracks.py   # tracks_final.json → 추적 결과 영상
python tools/draw_scene.py      # scene.json 영역을 첫 프레임에 겹쳐 그리기
python tools/evaluate/results_table.py > outputs/결과표_자동.md   # 평가 영상 결과표 (outputs/eval_auto + outputs/gt_cc)
```

## 새 영상 추가하기

1. 영상을 `data/videos/`에 넣는다. 압축본이 아니라 **원본 해상도**를 쓴다 (압축본은 탐지 결과가 달라진다).
2. 교차로 네 모서리를 정한다. 연석이나 횡단보도 안쪽 끝이 만나는 곳을 모서리로 본다. 모서리가 화면 밖이면 화면 끝(0 또는 1)으로 적는다. 방법은 둘이다.
   - `tools/pick_corners.py <영상 이름> ...`: 브라우저(http://localhost:8765)에서 첫 장면을 클릭해 찍는다. 앱의 장면 설정 화면을 흉내 낸 것이라 사거리/삼거리도 고른다. 저장하면 `scenes/cc_<날짜>_corners.json`을 만들고 영역 그림을 바로 보여 준다.
3. `src/make_scene.py`로 scene.json을 만든다 (`pick_corners.py`를 썼으면 이미 만들어져 있다). 앱에서 사용자가 누른 네 점으로 만드는 것과 같은 방식이다.
   ```bash
   python src/make_scene.py --video data/videos/cc/<영상>.mp4 --corners "x,y x,y x,y x,y" --frame-ref 30 --out scenes/<이름>.json
   ```
   삼거리(T자형)는 `--closed <방위>`로 길이 없는 쪽(화면 기준 north/east/south/west)을 준다. 그쪽에는 진입로를 만들지 않고, 장면과 facts에 `junction_type: "t"`가 들어간다. 판정 모듈은 이 값으로 삼거리 도표(차14-1 등)와 "삼거리 회전 차량" 수정요소를 고르고, 사거리 전용 도표(차18-2)는 뺀다.
   교차로가 아닌 장면(sample 같은 골목길)이나 진입로를 더 자세히 나눠야 하는 경우만 `docs/archive/schema_v0.3.md` 형식으로 직접 쓴다.
4. `tools/draw_scene.py`로 영역이 맞게 그려졌는지 확인한다.
5. `run_app.py`로 실행한다. 직접 쓴 scene.json은 결과 폴더에 `scene.json`으로 넣고 `--corners` 없이 돌린다.

## 좌표·데이터 규칙

- 좌표는 영상 크기 기준 0~1로 정규화한다.
- `bbox` = `[x, y, w, h]` (왼쪽 위 기준), `pos` = 박스 아래 중앙 (바퀴 위치).
- 시간은 `frame`과 `t`(초)를 함께 기록한다.
- 중간 결과(zones.json 등)에서는 판단할 수 없는 값을 `"unknown"`으로 둔다. facts.json에서 B가 계산에 쓰는 값은 `null`로 바꾸고 `unknowns`에 질문을 남긴다.
- 보간한 값은 `interp: true`로 표시한다.
- 클래스: `car`, `truck`, `bus`, `two_wheeler`, `bicycle`, `pedestrian`, `traffic_light`

## facts.json

필드 설명과 한계(예시 포함)는 `docs/facts_fields.md`에 있다. B가 요청한 명세는 `feature/B` 브랜치의 `judge/docs/FACTS_SPEC.md`다.

주요 필드만 보면 이렇다.

| 필드 | 내용 |
|---|---|
| `camera_type` | `cctv` / `blackbox` / `unknown` |
| `traffic_lights_detected` | 화면에 보인 신호등 목록 |
| `collision` | 순위가 가장 높은 충돌 하나 (프레임, 두 당사자, 위치). 순위는 `facts_fields.md` 7.1. 확정 못 하면 후보 1위를 `confirmed: false`로 |
| `parties.{id}.cls` | `car` / `truck` / `bus` / `two_wheeler` / `bicycle` / `pedestrian` (표가 갈리면 질문) |
| `parties.{id}.entry_from` | 들어온 진입로의 방위 (`north` 등) |
| `parties.{id}.intersection_entry` | 교차로 진입 `{frame, t}`, 모르거나 안 들어갔으면 `null` |
| `parties.{id}.intersection_entry_speed` | 진입 직전 5프레임 속도 (화면 비율/초) |
| `parties.{id}.stopped_before_entry` | 진입로에서 멈췄는지 |
| `intersection_entry_order` | 두 당사자의 진입 순서(1초 미만이면 동시)와 경계 오차에도 유지되는지 |
| `parties.{id}.movement` | 직진·회전. 들어온·나간 진입로로 정하고, 못 정하면 `unknown` + `movement_guess` |
| `parties.{id}.heading_start` | 회전하기 전 방향 (교차로 진입 직전 1초) |
| `events` | 등장, 영역 이동(`zone_type` 포함), 충돌, 정지 |
| `unknowns` | 사용자에게 확인할 질문 목록 (진행 방향, 진입 시점, 진입 순서, 종류, 신호등 유무, 부딪힌 두 객체) |

## 알려진 한계

자세한 예시는 `docs/facts_fields.md` 7장에 있다.

- 충돌은 하나만 쓴다. 가짜 충돌이 많아서(한 영상에 수십 개) 순위로 고르지만 여전히 틀릴 수 있다. 확정을 못 하면 후보로 대신하지만, 당사자 한 명을 아예 놓치면 후보도 틀린다 (cc_200303).
- 사전학습 YOLO(COCO)라 승용차·트럭·이륜차를 자주 혼동한다. AI Hub 데이터로 다시 학습할 예정이다.
- 속도는 화면 위 거리라 카메라와의 거리에 따라 다르게 나온다. 서로 다른 차의 속도는 비교하지 않는다.
- 기준값과 탐지 설정은 영상 세 개로 정했다. 비신호 교차로 CCTV 18개로 검증이 남아 있다.
- 영상 끝에 줌인 등 화면 전환이 있으면 그 지점에서 분석을 멈춘다.
